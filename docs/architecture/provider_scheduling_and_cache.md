## 调度输入

调度使用请求携带的分组、强制平台、客户端模型、映射后的模型、endpoint 和媒体意图、协议 transport、OAuth 和 privacy 要求，以及可选的 session 标识。提供商优先级只有一个来源：`providers.priority`。`provider_groups` 只记录成员关系，分组内没有单独的优先级。

普通请求读取分组内全部提供商的平台无关快照。平台为空的 `single` bucket 包含九类平台的提供商；指定平台的 bucket 用于专用入口或明确的能力选择。`/antigravity/*` 等强制入口额外加上平台过滤，分组成员、模型和协议门禁照常执行。所有请求都限定在请求的分组范围内，没有关联分组的提供商不会进入候选池。

同一个提供商可以属于多个分组。每个 bucket 的资格和模型范围单独计算，提供商的全局优先级在所有分组里一致。分组查询按 `providers.priority` 和 `provider_id` 稳定排序。

## 调度器模式

### 模式选择

`groups.scheduler_type` 是分组级的调度策略，取值为 `basic` 或 `advanced`，新建分组和历史上没有配置的分组都是 `basic`。每个分组都可以选择高级调度器，这个字段和平台能力无关；没有绑定分组的请求选不出提供商。

Claude Code-only、分组不可用等回退链由入口处理：入口重新检查目标分组的权限、资金和协议，并更新有效的 Key、分组快照和 `RoutePlan`。选择器只接受已经准入的分组；分组 ID 和上下文或 `RoutePlan` 对不上时，选择器拒绝选号，选号过程中不会跳到回退分组。回退链结束后，按最终落到的分组重新读取 `scheduler_type`。强制平台只缩小候选提供商的平台范围，最终分组、它的高级模式和参数覆盖都继续生效。

### 参数合并

高级分组的有效参数按字段合并。覆盖值的处理、深复制、校验和合并由纯规则包 `internal/scheduler/policy` 实现。选号和诊断直接使用其中的 `RuntimeSettings`、`EffectiveSettings`、`FeedbackConfig` 和 `StickyEscapeConfig`，运行反馈使用唯一的 `scheduler.RuntimeStats`；评分和 Top-K 抽样由 scheduler 负责。平台使用不含凭据的分数类型，执行目标和分数的对应关系只在本次适配调用内保存。

`scheduler.SettingsRuntime` 负责读取动态设置，带短 TTL 缓存和 singleflight，设置保存后发布到同一个实例。`scheduler.Parameters` 合并进程配置、运行设置和最终分组覆盖，app 把同一个参数实例绑定给各平台的选择和诊断。`GenericSelector`、`PlatformSelector` 和 `GeminiSelector` 决定基础和高级选择、粘性、订阅池以及 fresh 复核和数据库复核的执行顺序；`gateway/provider/selection` 里的 Generic、Compatible、Gemini 和 Diagnostics 负责把受控的提供商读取、平台资格和共享资源交给调度核心。

app 把反馈、设置和粘性统计各绑定一个实例，生产选择和诊断共用。运行设置和粘性观测都通过实例传递，进程里没有可替换的全局指针。

参数有三层：`scheduling.advanced` 是进程默认值，`advanced_scheduler_*` 运行时设置覆盖默认值，分组的 `advanced_scheduler_overrides` 最后覆盖。覆盖 JSON 里缺的字段继续继承；手动写的 `false` 和 `0` 都是有效的分组值，空对象表示全部继承。两个 EWMA alpha 分别控制错误率和 TTFT 新样本的权重，范围是 `0 < alpha <= 1`。sticky escape 的开关、TTFT 阈值和错误率阈值也按这个优先级合并。

运行时反馈按提供商共享，但请求完成时，用这个请求最终分组解析出的 alpha 回写，所以配置在请求途中保存也不会让选择和反馈错配。七项基础权重全为零也是合法策略：此时粘性加成仍然生效，完全并列的候选按提供商全局优先级和提供商 ID 稳定决胜，再进入 Top-K 抽样。负载和等待已经是评分信号，同分比较只有这一套规则。合并后的基础权重之和、完整权重之和都必须是有限数，管理端写入会拒绝让任一总和溢出的覆盖；请求时遇到历史遗留的异常对象，权重回退到已验证的全局值，计算结果始终是有限数，不会出现 `NaN` 或 `Inf`。基础分组和无分组路径忽略这份覆盖对象，残留配置不影响基础调度。

### 高级调度流程

基础调度器按优先级、最近使用、负载、粘性和等待选择提供商，它的排序和失败处理与高级调度器互不影响。高级调度器在各平台完成硬过滤之后才接管候选排序：

1. 适配层先执行硬过滤：分组、强制平台、模型、能力、提供商状态、限流、代理、privacy、配额、窗口费用和 RPM。
2. 通用核心对剩下的候选综合优先级、负载、队列、错误率 EWMA、TTFT EWMA、窗口重置和可选的会话粘性打分，在 Top-K 内做加权无放回抽样。
3. 暂时满槽或负载率 100% 的提供商，只要硬资格合格，仍然进入高级核心。选择前逐个复核实际并发槽，全部满槽时可以生成等待计划；无槽探测忽略占用情况。没有结果反馈时错误率按 0% 计算；负载快照、TTFT、窗口或平台专属额度缺失时使用中性值，提供商照常参与评分。
4. 高级调度器选出的请求，其转发结果、失败、TTFT 和切换会回写运行时统计；流开始后不能切换的规则保持不变。选定的提供商在补全凭据和数据库复核时，再检查一次分组成员、模型和协议；复核过的完整提供商数据以复核结果为准，旧快照覆盖不了它。

### 平台差异与粘性加权

Compatible 选择器在基础和高级调度中处理同组全部平台的候选，按实际提供商应用协议、模型、订阅优先和传输限制。Anthropic 检查窗口费用、RPM、会话上限和配额门禁；Gemini 复用已有的额度预检；Grok 检查免费层、团队模型冷却和媒体资格。Antigravity 按模型和协议能力参与调度，无需额外的混合调度开关。

关闭粘性加权时，已有的硬会话粘性仍然生效。OpenAI 的 previous response 不能跨提供商时，无论开关如何都保持硬绑定；能跨提供商时才作为加权信号。

共享的错误率或 TTFT 超过通用逃逸阈值时，只有当前请求逃逸，原来的绑定保留。开启粘性加权时，上一响应和会话所在的提供商只获得评分加成，和其他 Top-K 候选一起按权重抽样；它们不会被强制排到第一位，Top-K 都失败后也没有额外的保底尝试。window-cost 和 RPM 的 sticky-only 区间仍允许当前绑定的提供商进入评分。非 OpenAI 平台没有 previous response 绑定，诊断里这个信号标记为 `ignored`。

管理端列表通过 `provider/provider.SchedulerScoreOptions` 取得不含凭据的评分输入，app 注入生产选择共用的 `schedulerSharedState` 和设置 Store。Codex 额度余量的八小时有效期和次窗口折扣，只在 provider 模块计算。管理端的"高级调度评分"只对高级分组显示，使用同一个评分函数和候选池；评分展示仅供参考，提供商能否被选中仍取决于请求时的硬过滤。

### Codex 自动审查的父线程

Codex 自动审查请求和父线程的关联，只在以下条件下建立：模型为 `codex-auto-review`，Header 或 metadata 里有不冲突的 `guardian` 或 `review` 声明，并带有父线程 ID。`gateway/clientmeta` 解析这些字符串，HTTP 适配层提取 Header 并复用 scheduler 的会话散列算法，`requeststate` 只保存本次请求的新旧两个散列。查询限定在当前分组的粘性命名空间内，子请求无法覆盖父线程的绑定。普通模型、线索缺失或冲突时都不建立关联，这个关联也不代表任何身份授权。

### 短暂失败与选择适配

提供商和模型的短暂失败状态由 `provider.ModelTransientState` 持有，网关各调用点使用同一个实例；模型名先做平台规范化，再记录和查询。第一次失败只计数，第二次冷却 10 秒，连续三次及以上冷却 45 秒，成功一次清零。状态保留 30 分钟，有容量上限；这些状态只在内存里，进程重启后清空。

选择适配层通过只读的提供商接口和 `scheduler/rediscache.SnapshotReader` 取得候选或完整目标。完整记录在 Redis 适配层解码，评分和排序只接收不含凭据的数据。每次选择有自己的关联表，同一 ID 的快照记录、fresh 记录和数据库复核记录互不覆盖。进程 Options、反馈、参数缓存、会话和配额的持有者由 app 直接注入。普通 Grok 免费层和高级 picker 各有自己的缓存范围。

跨平台文本请求的资格判断和固定提供商 WS 的复核，共用 `gateway/provider.CompatibleEligibilityReason` 和协议能力判断。配额阈值、分组隐私要求和单次代理隔离绕过标记，保存在 `requeststate.ExecutionHints` 的值快照里；派生的 attempt 修改的是自己的副本，一次 fail-open 的标记只对当前请求有效。

## 评分诊断

管理员可以通过 `scheduler/httpapi` 的高级调度评分诊断，查看当前候选池的实时解释。候选、参数和解释由 `scheduler.DiagnosticService` 计算，selection 适配层只在单次调用中关联执行数据，凭据始终留在核心之外。基准诊断不指定模型、会话粘性和上一响应粘性。模拟诊断只接受模型和两个提供商 ID；session hash、previous response 内容、凭据和代理认证信息都无法传入。

诊断用不分页的分组全集统计排除原因，并复用生产服务里可以安全执行的检查：模型运行时封禁、额度、窗口费用、RPM、代理流隔离、OpenAI 和 Grok 配额自动暂停、影子母提供商健康、分组白名单。诊断只读：不获取并发槽、不注册会话、不写入粘性，也不修改运行时统计。endpoint、transport、Compact、媒体等需要请求输入才能判断的门禁，以 `not_evaluated` 策略信号返回，实际请求会在完整上下文里补做这些检查。

Spark 影子的母提供商资格由 `provider.ParentHealthyForShadow` 判断，调度、诊断和 WS 复核都使用这条规则：母提供商要存在、仍是 OpenAI OAuth，凭据没有因状态、到期或临时停调失效。母提供商自己的全局限流、过载和手动调度开关不影响影子。`provider/provider.DefaultSparkShadowModels` 在调用时根据 OpenAI 的 Codex 别名表构造一份独立的恒等映射，app 直接把它注入提供商管理，模型表只有别名表这一份。

评分核心在一次候选池里输出：

- `base_score = Σ(weight_i × normalized_i)`
- `final_score = base_score + sticky_bonus`
- `selection_weight = final_score - top_k_min_score + 1`
- `selection_probability = selection_weight / top_k_weight_sum`

开启粘性加权时，诊断显示的概率就是加上粘性加成后的 Top-K 抽样概率。

开启订阅优先且有可用的 ChatGPT 订阅提供商时，排名、Top-K 和概率只按订阅池计算，普通提供商标记为 deferred；订阅池不可用时才用普通池。关闭粘性加权、硬粘性提供商可用时，诊断保留它的原始排名和 `in_top_k` 状态，实际选择模式标记为 `sticky_forced_first`，被强制选中的提供商概率为 1，其他候选为 0。发生粘性逃逸时，原绑定的提供商按普通候选执行 window-cost 和 RPM 门禁；逃逸和缺少上下文的能力门禁作为独立的策略信号展示。

错误率和 TTFT 使用共享的运行时 EWMA。TTFT 的实测 `0ms` 参与延迟范围归一化；未观测的提供商使用中性值，全部已知样本相等时也保持中性评分。错误率的初始基线是 0%：没有反馈样本时按 0% 计算，归一化健康度为 1；第一次失败就会从零基线更新 EWMA，健康度立即低于从未观测过的提供商。每个聚合值还保存样本数和最近观测时间。诊断对没观测过的错误率显示"0%（未观测）"，负载、TTFT、窗口重置或平台额度快照缺失时标注"未观测，使用中性值"，这些提供商照常显示为可调度。负载的分母是提供商的 `EffectiveLoadFactor()`。分组覆盖、全局运行时设置和进程默认值都逐字段标注来源，诊断公式和实际高级调度使用同一组有效参数。

模型缺失错误的诊断由 `routing.ModelAvailability` 直接读取持久配置里的提供商池，app 把同一个 provider 存储和分组策略读取实例绑定到 Messages、兼容文本和已解析模型三个接口。这个查询忽略临时限流、过载和停调，同时复核分组、提供商协议路线和模型范围。判断模型是否存在要看持久配置，调度快照里候选池为空不能作为依据。候选限定在请求分组关联的提供商内，请求没有分组时不读取提供商池。HTTP 和计数执行端分别接收诊断能力和选择能力。已解析的模型直接使用，未解析的模型按 `PricingConfigService.ResolveRoutingModel` 的规则解析。

OpenAI 兼容选择、诊断和 WS 复核共用 `ModelPolicy.SupportsCompatibleRouting`，透传提供商同样遵守手动配置的白名单、映射和默认模型目录。

## 快照一致性

跨平台分组的调度 Redis 快照命名空间是 `sched:v5:`。OpenCode 的完整和轻量快照保留模式、已接受目录及人工模型协议覆盖，候选过滤按最终映射模型解析原生协议。解析结果把最终模型和协议一起交给执行方，自动探针同样检查模型协议的启用状态。完整和轻量两种提供商快照都带有 `upstream_protocols`、认证方式和 `responses_ws_connection_mode`，分组认证快照（版本 46）带有准入集合、转换映射和 Responses 图片策略。协议候选过滤在评分前执行，每次换号、fresh 复核和数据库复核时重新检查；转发目标只保存在本次的提供商副本里，共享缓存保持原样。

调度事件的格式、去重编码和 SQL 读写在 `scheduler` 和 `scheduler/postgres`。同一事务里写入的事件，提交后尽力发布。`scheduler.SnapshotService` 负责重建、事件消费和受限回退，网关读取和生命周期都直接绑定这个实例。`scheduler/rediscache` 负责 `sched:v5` 的快照发布、epoch 和 tombstone，bucket 锁继续使用 `sched:v4:lock:`，其中 `codec.ProviderCodec` 负责完整和轻量提供商的存储格式和字段过滤，使用 Provider 的字段名，并区分 nil 和空集合。

Gemini 配额预检在补全提供商凭据之前执行，轻量快照需要保存 `provider_type`、`oauth_type` 和 `tier_id`。第三方提供商跳过本地官方配额预检，官方提供商按保存的等级选取配额；遗漏这些字段会让候选被按默认档位过滤。服务启动和周期重建会从数据库重新生成快照，修复字段过滤后，已有缓存通过重建更新。

图片能力筛选也在补全提供商记录之前执行，轻量快照保留 `base_url`，使模型属性解析能够区分第三方中继与官方服务。OpenAI 兼容中继中的 Gemini 图片别名可以通过分组的 `reference_model` 继承图片能力；丢失地址会改变引用目标的服务身份，导致探针或图片请求被误判为能力未知。该字段通过现有的启动和周期重建进入已有缓存，无需修改分组属性配置。

app 把 provider 和 routing 的存储、凭据刷新后的提供商记录绑定到同一个缓存，执行目标通过 app 注入的受控读取接口取得。编码器内部持有完整记录，核心只读取不含凭据的候选元数据。执行凭据由 provider 模块受控提供，分组数据从 routing 读取。

`scheduler.SnapshotService` 管理 bucket 快照和提供商数据。启动时异步执行初始重建，outbox 立即消费第一轮；运行中持续消费调度 outbox，并定期全量重建，修复漏掉的通知和外部写入。提供商状态的热更新可以先发布快照，再通过 outbox 和失效通知更新相关缓存。

一致性保护措施：

- bucket 写入带 token 和 epoch，较慢的旧重建无法覆盖新状态。
- 已退役的 bucket 写 tombstone，延迟到达的事件无法重新打开已删除的分组。
- 分组生命周期 lease 协调 reopen 和 retire，Redis 锁保证同一 bucket 同时只有一个重建。锁句柄带随机 owner token，释放时比对 token，旧持有者超时后删不掉继任者的锁；锁的 key、字符串存储类型和 TTL 不随版本变化。
- 提供商变化、分组变化、批量变化、last-used 和全量重建使用不同的事件，热字段更新只重算受影响的部分。

快照未就绪或读取失败时，可以有限度地回退到数据库。回退有单独的超时和 QPS 上限；超过上限时返回 cache-not-ready 或 fallback-limited 类错误，防止故障期间所有请求同时打到数据库。提供商配置以数据库为准，快照是转发热路径上的副本；两者短暂不一致时，靠版本栅栏和后续重建恢复一致。

快照运行时重复调用 Start 时跳过启动和重建。Stop 取消周期任务、排队任务和支持 context 的在途操作，在应用剩余预算内等待；Stop 后无法重新启动。等待超时时，任务可能没完成，持久 outbox 也可能没排空。

消费水位按事件 ID 推进。如果一个 ID 较小的事务在水位越过它之后才提交，这个事件可能被跳过，由定期全量重建修复。清理时的十秒宽限只推迟删除，已经越过水位的旧 ID 不会被重新轮询。

## 候选筛选与评分

候选提供商依次按以下条件缩小范围：

1. 分组关联、强制平台、active、schedulable 和提供商有效期。
2. 提供商级、模型级和 endpoint 级的临时不可调度、限流恢复时间和配额状态。
3. 客户端模型映射后的最终模型、白名单和提供商 capability。
4. OAuth-only、privacy、客户端类型、站点和区域、媒体资格，以及需要的 transport。
5. 当前并发槽和等待策略。

Bedrock 提供商的模型筛选，会统一解析型号、来源区域和全局推理开关。找不到已核实有效路由的提供商不会进入候选；模型目录和持久可用性诊断使用同一套判断。优先级和未知规则的处理见 [Bedrock 模型与来源区域](../interfaces/anthropic_upstream.md#bedrock_region_routing)。

通过硬过滤之后，才比较优先级、近期使用、提供商负载、排队、错误率、延迟、重置窗口或配额余量。高级核心提供跨平台统一的评分和 Top-K 选择；OpenAI 和 Grok 适配器只在请求确实需要时，补充 Responses transport、WebSocket、旧版 `/responses/compact`、原生 `remote_compaction_v2`、previous response、订阅和额度信号。原生 V2 使用普通的 Responses 模型路由，单独读取管理员配置的 `openai_native_compaction_v2_mode`，历史探测状态和旧版 Compact 开关都不影响它。

压缩能力只在管理员关闭时排除；开启时仍然要满足普通 Responses 端点的能力要求。调度元数据需要保留两种压缩开关和文本路由配置。压缩资格只有启用和关闭两种状态。快照里显示关闭的提供商，仍然可以在最后做数据库复核，这样管理员重新启用后，它不会因为旧快照被一直漏选；数据库确认关闭的提供商拿不到最终调度资格。

评分只使用调度信号；上游声明倍率、OAuth 参考倍率和 `upstream_cost` 权重都不参与排序。提供商本地的 `rate_multiplier` 和共享价格配置的上游计费模型来源只用于结算。新增评分项要在硬资格判断之后生效，缺少观测数据时按中性值处理，提供商仍然可用。

## 提供商自动停调阈值

数据库运行时设置 `provider_scheduling_thresholds` 接受 `openai`、`anthropic`、`grok`、`kimi` 和 `zhipu`，值为 1 到 100 的整数。OpenAI、Anthropic 和 Grok 的缺省值为 100；Kimi 和 Zhipu 省略且没有提供商覆盖值时，评估器跳过这项门禁。100 表示关闭门禁。提供商凭据里的 `provider_scheduling_threshold` 可以覆盖平台默认值，同样限定 1 到 100，浮点数四舍五入到最近的整数。Gemini、Kiro 和 Antigravity 即使带有观测字段，也不参与这项门禁。

每次调度候选前，用当前的额度快照评估阈值：

- OpenAI：读取身份匹配、尚未重置、也没超过自动暂停陈旧期限的 Codex 5h 和 7d 窗口。`codex_*_used_percent` 始终按 0 到 100 的百分数解释，`1.0` 表示 1%。
- Anthropic：utilization 字段按 0 到 1 的比例换算成百分比。
- Grok：只读取响应头里的滚动 quota 窗口，官方 7d 和 30d 账单周期不参与。
- Kimi、Zhipu：读取 Coding Plan 的统一用量快照，使用 `limits` 中的用量百分比和重置时间。

多个窗口同时达到阈值时，取重置时间最晚的窗口作为暂停截止时间。快照已过期、明确陈旧、缺少截止时间、身份不匹配或没有观测数据时，提供商不会被暂停。

历史快照缺少 `codex_usage_updated_at` 或无法解析时，按 fail-closed 处理，门禁照常生效。

命中阈值后，服务写入带结构化来源的临时不可调度原因和窗口截止时间，并触发提供商状态的失效传播；阈值状态没变时不重复写入。管理员可以从暂停原因区分阈值门禁和普通限流。设置读取使用进程内原子缓存，回源时用 singleflight 合并。配置项不存在时，默认阈值按正常 TTL 缓存；只有实际的数据库故障才使用较短的错误 TTL。保存设置后立即替换缓存；部分更新没带这个字段时，现有缓存保持不变。

OpenAI 和 Grok 的进程内停调、同一提供商的 429 恢复窗口和刷新失败的发布版本，统一由 `provider.RuntimeBlockState` 持有，app 把同一个实例绑定给执行和恢复两边。Grok 回滚暂定停调时，只撤销本次安装的那个版本；之后被延长或重新声明的停调保持有效。凭据版本阻断使用 `RefreshFailureBlocks`，没有匹配的版本时跳过身份散列计算。平台资格和记录数据由执行适配层负责。

## 粘性与等待

手动指定的 session、previous response、WebSocket 或平台内部上下文都可以建立粘性。命中粘性的提供商仍要通过当前快照的状态、分组、模型和策略校验；提供商被禁用、移出分组、被限流或能力不再满足时，旧绑定失效。

app 分别构造一个 `scheduler.SessionLimitCache` 和一个 `billing.WindowCostCache`，网关通过两个接口使用它们。会话注销只操作调度会话；窗口费用的 key 前缀是 `window_cost:provider:`，缓存 TTL 30 秒。两类数据共用 Redis 客户端。

Anthropic OAuth 和 Setup Token 提供商的 `max_sessions` 限制空闲窗口内的活跃会话数。Messages 请求正常成功（包括流式和换号后成功），或者返回可结算的部分结果后，成功提供商上的会话注册保留，按最后活动时间和空闲超时过期；请求结束时只释放请求并发槽。没有成功的请求和被放弃的提供商 attempt，立即注销对应的会话，失败的请求不会占满空闲窗口。

粘性提供商的并发槽和有界等待队列都满时，负载感知选择可以让这一个请求临时使用其他合格的提供商。这种容量溢出不改写持久的粘性绑定，之后的请求仍然优先回到原提供商。

并发已满、但候选可能很快空出来时，请求进入有界等待队列。等待使用轮询退避、总截止时间和上下文取消；等待结束后重新选择，过期的选择结果会被丢弃。"没有任何长期合格的候选"和"暂时没有并发槽"是两种不同的错误，前者直接返回，不进入长时间等待。

请求资源的归属由 `Lease` 和 `AttemptLease` 表示：用户槽、API Key 统计和确实拿到的等待计数属于请求租约；提供商槽、串行锁和会话登记属于当前尝试。资源拿到后立即登记，补全完整提供商或协议复核失败时回滚，重复释放只生效一次。增加等待计数失败时照常放行，没有确认拿到的计数不做递减，结果不确定的计数靠 TTL 自动清理。同步的 `WaitObserver` 只负责通知 HTTP 输出心跳，SSE 格式、Flush 和写失败处理都在 HTTP 层。

会话批量查询使用支持冷启动的 Lua 调用：Redis 脚本缓存被清空后照样执行查询，NOSCRIPT 不会被当成会话不存在。`AttemptLease.Finish` 根据实际成功、可结算的部分结果或失败，决定保留还是注销会话；物理槽提前释放和逻辑上的服务失败是两回事。WS 入站和 Live 租约各自独立，图片的本地限流和 Redis 提供商池分开计数。

释放方式由调用方选择。Qoder 已经进入上游的流式请求采用完成后释放：客户端断开时只停止下游写入，仍在预算内收集尾部 usage 后再归还资源；等待中和非流式请求的取消按各自的规则处理。实际业务输出开始后能否重试，由网关执行层判断，scheduler 不维护自己的 failover 循环。

## 失效与恢复

以下变化需要让相关的提供商数据或 bucket 失效：提供商启停和删除、凭据刷新、分组关系、优先级、模型映射和白名单、代理可用性、限流和临时不可调度、privacy 和可调度资格。提供商变化时，同时更新它所在分组的平台无关桶和相关平台桶；删除提供商或无法确定原平台时，重建受影响分组的全部桶。

数据库写入成功但失效广播失败时，记录一条可操作的告警，靠定期重建恢复一致。数据库、Redis 快照和进程内缓存需要按更新路径保持一致；只发通知、不保存数据库状态，重建后又会回到旧值。

提供商 extra 的原子合并只保留仍然有效的系统状态，例如 Ollama Cloud 的管理会话和用量快照。凭据或代理变化时，按各自的规则保存或清除 Ollama 状态。历史字段 `upstream_billing_probe` 和 `upstream_billing_probe_enabled` 在所有写入路径上直接丢弃，它们不触发任何 CAS、outbox 或调度快照失效。

API Key 的上游用量查询属于控制面，结果只存在浏览器缓存里，调度缓存、数据库和提供商 `Extra` 都不保存它，所以查询失败不影响转发；上游查询有自己的并发槽，不占用网关的提供商调度槽。缓存规则见 [API Key 上游用量查询](../interfaces/upstream_usage.md)。

## 认证快照

### 分组定价快照

认证缓存版本为 47。认证模块维护缓存 key、TTL 和 jitter、负缓存、发布订阅及 outbox 延迟二次失效规则。快照是否完整由版本号判断，与旧媒体字段是否为空无关。认证快照里的 `RoutingPolicy` 保存独立的模型策略和功能策略，映射、白名单和嵌套的功能值在每个请求中都深拷贝一份。`ModelPricing` 保存完整的分组价卡，包括上下文区间、Fast 和 Flex、Max 推理和分时规则。普通 Key 和复合 Key 使用各自的分组数据副本；单个请求修改金额指针、模型列表、区间或分时段时，改的是副本，缓存保持原样。分组更新的事务提交后，使用现有的按分组失效机制；价格继承和价格展示使用同一套解析规则，见[分组模型价卡与倍率继承](../domains/routing_and_billing.md#group_model_pricing)。

### Key 认证快照的归属

认证缓存和回源并发控制由 `apikey` 模块负责，Redis 实现在 `apikey/rediscache`，失效 outbox 的存储在 `apikey/postgres`。每次返回一份独立的请求副本；复合 Key 选组、模型映射和分组回退修改的都是这份副本里的 map、slice、指针和嵌套策略。Redis 重连时重新订阅，并安全清理缓存；关闭时等在途操作结束后，再关闭订阅和 L1 缓存。

## 排查要点

- "无可用提供商"的诊断要区分：没有分组关联、被硬资格过滤、模型或 endpoint 不匹配、临时限流、并发等待超时、快照不可用。
- 日志和 Ops 记录提供商 ID、bucket、平台、模型和过滤原因；token 和完整凭据不写入日志。
- 修改筛选或评分时，测试要覆盖缓存命中、数据库回退、粘性命中后失效、并发更新的乱序事件，以及流开始后的失败。
- 管理端提供商测试成功，只说明测试用到的协议可用；调度仍按实际 endpoint 判断能力。
