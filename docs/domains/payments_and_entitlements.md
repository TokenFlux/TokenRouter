# 支付与权益

本文描述余额、订阅、兑换码和支付订单如何产生和撤销可消费的权益。修改支付或权益发放时，用本文核对金额、状态机和幂等的不变量。支付提供商的接入参数、运营配置步骤和对外接口手册见库外的支付指南。

## 权益模型

| 概念 | 作用 | 状态保存在哪里 |
| --- | --- | --- |
| 用户余额 | 没有适用的订阅或订阅不够时，承担网关消费 | 用户余额和冻结金额，通过领域仓储原子调整 |
| `SubscriptionPlan` | 可以出售或人工发放的权益模板 | 价格、币种、有效期、日/周/月额度、覆盖的分组和分组倍率 |
| `UserSubscription` | 某个用户实际拥有的、带时间窗口的权益 | 起止时间、active/pending/revoked 状态、额度快照、使用量和可选的来源订单 |
| `RedeemCode` | 可以使用一次或有限次数的权益发放凭据 | 类型、值或套餐、有效期、最大次数、状态和用户兑换记录 |
| `PaymentOrder` | 外部资金事件和内部权益发放之间的协调记录 | 金额、币种和费用、订单类型、提供商和商品快照、状态、各时间点和退款字段 |

billing 负责余额的原子调整、订阅、套餐和兑换规则；SQL 和 Ent 实现在 `billing/postgres`，HTTP 和 DTO 在 `billing/httpapi`。payment 负责支付配置、订单、渠道绑定、查单和履约、退款编排；promotion 负责邀请码、返利和 Promo。支付和推广直接调用 billing 的权益接口，套餐规则只在 billing 里维护。用户端和管理端的套餐接口分别保持公开展示用的格式和历史的 Ent JSON 格式。

订阅计划是可以修改的商品配置，用户订阅才是已经发放的权益。购买订单保存计划快照，履约按下单时的价格和权益执行；管理员之后修改或删除套餐，已付款的订单不受影响。余额订单和订阅订单共用支付确认流程，确认后进入不同的履约分支。

## 订单与快照

创建订单前，依次校验：用户归属、支付功能开关、订单类型、提供商实例、支付方式、币种、金额范围、套餐是否在售、促销规则。`out_trade_no` 是发给外部提供商的唯一商户订单号，新订单由 `tr_`、日期 `YYYYMMDD` 和 8 位随机字母数字组成。本地的数值 ID 用于内部查找。

历史订单继续使用创建时的商户订单号，查单和回调按完整的 `out_trade_no` 匹配。查询未命中时，早期的 `sub2_<本地订单 ID>` 格式可以按数值 ID 查找订单。`tr_` 订单号按完整值查询。

订单持久化以下创建时的信息：

- 应发权益金额 `amount`、实际支付金额 `pay_amount`、费率和固定费用，以及币种。
- `order_type`、订阅订单的 `plan_id` 和 `plan_snapshot`。套餐快照包括下单语言、当时展示的套餐名称和商品名称。
- `provider_instance_id`、`provider_key` 和 `provider_snapshot`，回调、查单和退款使用订单当时的实例。`display_locale` 与 `display_subject` 固定渠道使用的商品描述。
- 客户端来源、过期时间、外部 trade number、invoice 和 receipt 信息，以及每次状态变化的时间点。

`payment.Runtime`、`ConfigService`、`ProviderBindings` 和选择器由 app 直接装配，HTTP 和后台使用同一组下单、查询、履约和退款实例。具体渠道的构造、密钥和环境信息留在渠道适配层。第一次读取实例失败时不标记为已加载；刷新时先构造完整的候选表再原子发布，整体读取失败时保留旧表并允许重试，单个配置损坏时跳过它。

提供商实例决定支持的支付类型、模式、限额、排序和退款能力。删除或修改当前实例后，历史订单仍按原来的实例解释；只有解析旧订单时，才按保存的 provider key 或兼容注册表回退。

套餐介绍、权益、支付帮助和自定义方式名称的翻译规则见[用户侧国际化](../interfaces/user_localization.md#content_owners)。

## 支付统计与展示单位

账户到账金额、余额和订阅额度使用配置的余额单位；实际支付金额使用订单保存的支付币种。支付仪表盘按币种分别汇总收入、购买分布和平均购买单价。`purchase_distribution` 的每条记录带有 `currency`，同一套餐或按量支付类别在不同币种下有独立记录；前端先选择币种，再计算该币种内的金额和订单数占比。

订阅订单的 `amount` 是原始套餐价格，`amount_currency` 来自下单时的套餐快照；`pay_amount` 和手续费使用支付通道的 `currency`。创建订单、用户查询、公开支付结果和管理员查询都返回这两个币种，页面分别格式化原价和实付金额。余额订单省略 `amount_currency`，到账数量继续使用自定义余额单位。启用 USD 到 CNY 换算时，未填写币种的套餐在订单快照中记录 USD；历史快照没有可用套餐币种时，原价显示沿用订单支付币种。

`avg_reasoning_point_purchase_unit_price` 返回币种到单价的映射。每个币种的单价等于该币种的本金合计除以购买单位合计，保留四位小数。本金取实际支付金额减手续费；购买单位取余额订单的到账金额，或订阅快照的月额度。非正本金、非正到账金额和没有正月额度的订阅不参与。`reasoning_point_purchase_order_count` 是所有币种的参与订单总数。展示格式为“支付币种 单价/自定义余额单位”。

## 支付状态机

正常的成功路径：

```text
PENDING -> PROCESSING -> PAID -> RECHARGING -> COMPLETED
    |          |            |          |
    |          +----------> EXPIRED    +-> FAILED -> retry
    +-> CANCELLED / EXPIRED
```

- `PENDING`：订单已创建，用户或管理员还可以取消。外部报告处理中时，用条件更新进入 `PROCESSING`。
- 支付成功时，先核对金额是有限的正数、和订单在币种最小单位的容差内一致，再从 `PENDING`、`PROCESSING`、`EXPIRED` 或 `CANCELLED` 进入 `PAID`。本地已经超时的订单收到晚到的成功，同样会进入 `PAID`，实际付款不会丢失。
- 履约通过条件更新取得一个有时限的 `RECHARGING` lease；只有 lease 的持有者能发放权益并进入 `COMPLETED`。
- 履约出错时进入 `FAILED`，管理员或后台对账可以重试；`RECHARGING` 卡住超过 lease 时限后，也可以被安全接管。
- 提供商明确返回失败时，尚未付款的 `PENDING` 或 `PROCESSING` 订单记为 `EXPIRED`。未知或不支持的回调状态按未确认处理。

订单已经关联外部支付时，取消和过期前先查单；提供商显示已付款或仍在处理时，订单保持当前状态。调用上游取消失败后，再查一次单，处理付款和关闭同时发生的情况。所有状态迁移都以旧状态为条件更新；竞争失败后重新读取当前状态，按实际的终态返回。

<a id="forced_expiration_recovery"></a>
### 强制过期与失败退避

用户取消、管理员的普通取消和后台超时关闭都按 fail-closed 处理：查不到上游状态时，接口返回 `PAYMENT_STATUS_UNAVAILABLE`，订单保持 `PENDING`，可能已经付款的订单不会被直接关闭。第一次失败时写入 `PAYMENT_CANCEL_FAILED` 审计，并刷新订单的 `updated_at`；超时 worker 等上次失败超过 15 分钟后才重试，错误的地址或暂时的故障不会导致每分钟重复查单。

管理员可以对单笔 `PENDING` 订单执行强制过期，需要填写 1 到 500 个字符的原因。这个操作不访问上游，在同一个事务里用条件更新写入 `EXPIRED`，并记录 `ORDER_FORCE_EXPIRED` 审计；审计写入或提交失败时整体回滚，状态已经变化时返回冲突。它是管理员手动的恢复手段，普通取消和自动过期照常按上面的规则工作。有效的迟到付款通知仍然可以把订单从 `EXPIRED` 带到 `PAID`，再按幂等履约流程处理。

只要还有处于 `EXPIRED` 状态的 `ORDER_FORCE_EXPIRED` 订单，它对应的 provider instance 可以禁用，但不能硬删除，因为回调验证和迟到付款的恢复还需要这个实例的历史凭据。订单离开过期状态后，这个限制自动解除。

<a id="callback_security"></a>
## 回调安全

Webhook 路由不使用用户 JWT，所以提供商验签、订单绑定和金额验证就是它的授权检查：

1. 限制请求体大小，按提供商的要求读取原始的 body、query 和必要的 header；重新序列化会改变签名输入，所以在验签前保持原样。
2. 尽量从商户订单号找到原订单对应的 provider instance；有多个实例且无法预先判断时，逐个尝试验签，只有验签成功的实例才能解释这条通知。
3. 验证 provider 自己的签名、时间戳和重放窗口、事件类型，再验证通知里的 provider、trade number 和订单 metadata 与本地快照一致。
4. 核对通知金额是有限的正数，并且与订单的 `pay_amount` 在币种容差内一致，然后才进入 `PAID`。
5. 无关的事件，按提供商的要求返回成功响应；验签或处理失败时返回失败，让提供商重试。本地确实不存在的订单，可以确认接收以停止无意义的重试，同时记录告警。

易支付的 MD5 协议直接拼接参数值，浏览器中的下单 URL 带有签名。`EasyPay.VerifyNotification` 在验签前检查字段白名单：`pid`、`trade_no`、`out_trade_no`、`type`、`name`、`money`、`trade_status`、`param`、`sign`、`sign_type`。出现白名单外的字段或重复字段时拒绝通知，空值字段也参与检查。

字段名白名单需要配合字段内容校验：`pid`、`trade_no`、`out_trade_no`、`type`、`money`、`trade_status` 都需要非空，含 `&`、`=`、NUL、回车、换行或首尾空白时拒绝。`type` 使用和自定义支付方式配置相同的格式，接受小写字母、数字、下划线和连字符。`pid` 需要匹配验签实例，金额需要是有限的正数。商品名称和可选 `param` 支持自由文本。所有参数按协议解码一次后验签，入账前再与订单快照核对商户和金额。

下单时，`CanonicalizeReturnURL` 校验用户提供的结果页地址，拒绝 URL 用户信息（userinfo）以及主机名中的 `&`、`=`。它使用校验后的 scheme、host 和固定 `/payment/result` 路径重建 URL。服务端随后生成 `order_id`、`out_trade_no`、`resume_token` 和 `status` 参数。结果页参数用于找回订单和展示页面，付款确认依赖回调验签或上游查单。

回调是主要的信号。主动 verify、查单和后台 reconcile 用于漏掉回调、弹窗支付或进程中断后的恢复，它们和回调调用同一套状态迁移和履约函数，加余额只发生在履约函数里。易支付兼容平台携带白名单外的通知字段时，回调会被拒绝，订单可通过主动查单确认付款。

## 履约与幂等

余额订单通过订单专属的 `recharge_code` 复用兑换领域的原子权益调整：代码不存在时创建；存在但还没使用时继续兑换；已经使用时只补完后续步骤。订单级返利有自己的审计去重，兑换层在这条路径上跳过返利，所以返利只计一次。权益和适用的返利都完成后，持有 lease 的调用者才能用条件更新把订单改为 `COMPLETED`。

订阅订单调用 `AssignOrExtendSubscription`，把 `source_order_id` 设为订单 ID。服务在事务里锁住用户行，再查询来源订单和同一套餐最新的订阅，同一用户的并发发放因此先排队，再依次延长时间链；已经有这个来源订单的订阅时直接复用，所以 webhook、查单、人工 retry 和后台 reconcile 不会为同一订单重复发放。同一套餐当前还没过期时，新订阅从上一份的 `expires_at` 开始，状态为 `pending`，两份订阅按时间先后衔接。

`payment.OrderExpiry` 的 Start 和 Stop 可以重复调用，停止后无法重启；运行 context 贯穿锁、查询和渠道请求，取消后不再进入下一项或下一阶段。app 让它启动后立即执行第一轮，之后按固定周期执行，用 leader key 选出执行者，Redis 不可用时回退到数据库。后台总预算 30 秒，超时不代表已经排空。

支付审计日志记录下单之后的重要动作、操作者和详情。通知邮件等副作用在完成后异步派发，发送失败不会回滚已经发放的权益；通过订单的完成状态和审计动作避免重复通知。

## 退款

退款只能从允许退款的已完成余额订单、并且配置为可退款的 provider instance 发起；用户自助退款还要求实例开启 `allow_user_refund`，并满足业务资格。退款相关的状态有 `REFUND_REQUESTED`、`REFUNDING`、`REFUND_PENDING`、`PARTIALLY_REFUNDED`、`REFUNDED` 和 `REFUND_FAILED`。

`payment.RefundWorkflow` 协调 `payment/postgres.RefundStore` 的几个短事务，通过 app 注入 billing 的 Ent 同连接参与能力。退款先扣回权益，渠道明确失败或待确认时再补偿；调用渠道期间不持有数据库事务。

1. 准备事务：锁定并认领订单，写入实际预扣的金额和 `REFUND_PREPARED` 恢复记录。恢复记录包含格式版本、本地操作标识、订单版本、扣减意图和实际扣减值、订阅信息。任何一步失败都整体回滚，渠道不会被调用。
2. 在事务外调用渠道。Stripe 用订单号和最小货币单位的退款金额组成幂等键，本地操作标识不参与渠道编码。
3. 渠道明确失败或 pending 时，补偿、订单状态和必要的审计在同一个事务里提交。补偿或审计失败时，保留准备阶段的扣减和 `REFUNDING` 状态，并返回错误。
4. 渠道立即成功时，提交成功状态和成功审计；权益在准备阶段已经扣过，这一步不再扣减。这个事务失败时，外部退款可能已经完成，本地保留准备阶段的记录并返回错误。
5. pending 最终成功时，在同一个事务里复核认领状态、版本和退款身份，再回收权益、更新状态、写成功审计。迟到的失败结果不会覆盖较新的成功结果。

管理员的退款查单入口也接受带有效恢复记录的 `REFUNDING` 订单：它查询已经发生的渠道操作，并幂等地完成退款流程，渠道上的退款只发起过那一次。旧的 `REFUND_PENDING` 字段继续兼容。恢复资料缺失、损坏或互相矛盾，或者渠道不支持查单、结果不明确时，要求人工核实；系统不会假设扣减为零并自动完成。普通支付过程的审计尽力写入；退款正确性依赖的记录必须持久化。`(order_id, action)` 唯一索引保持不变：同一动作的后续尝试更新当前版本，旧的详情原样归档到 `history`，并记录操作标识和时间，旧的退款记录不会被删除。旧 pending 记录里明确写了 `deductBalance=false` 时，这个值优先；没有这个字段和写了 `false` 是两回事。

回退到不认识准备记录的旧版本之前，先处理或登记所有未完成的退款；删除这些记录后盲目重试，会丢失退款的进度。

余额退款在非强制模式下发现余额不足时，返回 `require_force`，管理员明确确认后才能继续。强制退款也只能原子扣除当时可用的非负余额，实际扣减的金额写入结果和审计。订阅相关的退款，需要识别由 `source_order_id` 发放的订阅，以及它们处于 active 还是 pending。强制退款是管理员明确发起的操作，需要记录理由；普通的错误恢复走上面的查单和补偿流程。第一次尝试返回 `require_force` 时，管理端保持退款弹窗打开，显示服务端的警告；管理员勾选强制确认后，才带上 `force` 重试；关闭或重新打开弹窗时，清除上一次的确认状态。

## 订阅生命周期

用户订阅复制发放时的有效期和日、周、月额度。状态的含义：开始时间已到的有效记录是 `active`，未来排队的记录是 `pending`，人工撤销的是 `revoked`；软删除也按 revoked 处理。能否消费还要求：当前时间在 `[starts_at, expires_at)` 内，所有已配置的有限额度窗口都没用完，并且在套餐的分组范围内。

套餐的分组为空，表示这个套餐不限制分组；非空时，表示可以消费的分组集合。用户的订阅列表用 `groups_restricted` 和带名称的 `applicable_groups` 展示这个区别。只有 API Key 明确选择了这个订阅时，Key 可选的分组才收窄为用户已有权限和这个集合的交集；自动结算和只用余额的 Key，可选分组保持用户原有的权限范围。指定订阅的付款主体按 Key 的归属确定，团队 Key 使用 Team Owner 的订阅。

套餐保存时，服务端核对提交的分组是否仍然存在，指向已删除分组的 `group_ids` 返回 `GROUP_NOT_FOUND`，写入不会落库。删除分组只清理分组授权和提供商关联，套餐里记录的分组 ID 保留下来，所以订阅列表读取时会把确认已删除的分组从 `applicable_groups` 中去掉，查询失败时仍保留只有 ID 的条目。管理端编辑套餐时也会丢弃已删除的分组和它们的倍率覆盖，保存后套餐记录随之修正。只提交价格、额度等字段而不带 `group_ids` 的更新保留原分组选择，不做分组查询，因此已经记录了旧 ID 的套餐仍可修改其他字段。

<a id="subscription_quota_windows"></a>
### 周期额度窗口

每种周期额度有自己的窗口起点和累计值，重置服务按项目时区推进窗口。日额度按日历日对齐，每天 0 点刷新；激活或手动重置时写入当天 0 点，历史上非零点的起点会在下一个 0 点之后自动修正为当天 0 点。周额度和月额度按 7 天和 30 天的窗口推进。

订阅快到期时，按"日 < 周 < 月"的外层有限额度来保护：

- 日窗口：配置了正数的周额度或月额度时，即使订阅剩余不足 24 小时，日额度也可以刷新。
- 周窗口：配置了正数的月额度时，即使剩余不足 7 天，周额度也可以刷新。
- 月窗口：上面没有更高层的保护，订阅剩余时间需要能容纳完整的 30 天窗口。

没有配置、为零或为负的额度表示无限，这样的额度起不到保护作用。有效期不超过 1 天的订阅，日额度始终是一次性的，外层额度不会让它再刷新一次。

事务结算会把订阅承担的消费同时累计到所有已配置的有限窗口，所以低层窗口在尾段刷新只恢复短周期的可用量，外层的累计值仍然是新请求的硬性准入上限。普通请求通过预检并成功完成后，如果最终费用超过了指定订阅的剩余额度，事务把订阅用量封顶在可用额度，没有覆盖的基础用量按余额倍率从付款主体的余额扣除，余额不足时可以变成负数欠费。这样结算不会因为封顶而回滚，请求也不会变成零计费。这笔欠费只用于结算已经放行或并发在途的请求，用户并没有因此得到额外的权益；之后绑定这个订阅的新请求仍然按 `used >= limit` 拒绝，余额充足也一样。

批量任务提交上游前的额度预占不适用这个例外，指定订阅不能完整覆盖时回滚并拒绝。服务层预检、额度进度展示和数据库事务的归一化，使用同一套尾段规则，缓存判断和最终扣费的结果一致。结算在数据库事务里锁定并累计当前用量；读取缓存只用于热路径的预检，提交后的缓存和认证失效按各入口现有的顺序执行。目前的 `InvalidateSubCache` 是一个空的兼容入口，它既不广播，也不让其他实例失效。

同一用户同一套餐的连续订阅组成时间链。管理端的延长、撤销、有效期调整和重置，都在事务里先锁用户，再读取最新的订阅和时间链；两个并发的延长会累加，后提交的不会用旧快照覆盖先提交的。有效期调整会加入已有的外层事务，外层回滚时全部撤销。延长或调整有效期时，后续的 pending 记录保持不重叠；恢复已撤销的记录时，也要重新计算它在链上的位置。`source_order_id` 是支付发放的幂等键；人工发放、注册默认发放和兑换码发放没有来源订单，各自用自己的事务和锁保证不重复。

<a id="subscription_self_revoke"></a>
### 用户自助撤销

用户只能撤销本人当前 `active` 的订阅，并且只在最高层已配置的正数有限额度用完时开放：先看月额度，其次周额度，最后日额度。低层窗口暂时用完，或者套餐没有有限额度时，都不能撤销。`POST /api/v1/subscriptions/:id/revoke` 在同一个事务里复核状态和额度，软删除当前记录，并把后面同一套餐的链往前移，第一份 pending 订阅因此立即生效。有接续的订阅时，所有 `billing_mode=subscription` 并且绑定了旧订阅 ID 的个人、团队、复合和托管 API Key，一起改绑到接续的订阅；没有接续时，旧绑定保持不变，这些 Key 变为不可用。撤销不退款，用户也无法自行恢复。

订阅过期和到期前 7、3、1 天的提醒由 billing 的维护器扫描，邮件模板、收件人处理和投递由 notification 负责，见[通知与邮件投递](notification_delivery.md)。app 注入时钟、独立的操作预算和 leader 锁策略，构造期间不启动任务。

<a id="redeem_eligibility"></a>
## 兑换码

管理员生成的自定义兑换码最多 32 个 Unicode 码点，常用汉字、生僻汉字和英文字母各计一个。前端提交校验、生成接口参数、管理服务和 Ent 写入校验都按码点数限制长度。前端提交和管理服务创建前会去掉首尾空白。前端在超长时提示用户修改，并保留输入内容。数据库字段为 `VARCHAR(32)`。列表和导出共用搜索词处理：去掉首尾空白，再截取前 100 个码点。

兑换码可以发放余额、并发或订阅权益；邀请码不能在用户兑换入口产生权益。服务先限制用户的失败次数，再用代码级的短期锁让请求排队；仓储在事务里锁住代码，校验状态、有效期、最大使用次数和"同一用户只能用一次"的记录，并原子写入权益调整和使用记录。

管理员创建或单条编辑余额、并发和订阅兑换码时，可以设置 `requires_payment`，默认关闭。开启后，领取者需要有至少一笔本人支付订单，其 `paid_at` 已写入且 `pay_amount > 0`，金额不限。后续履约失败或退款仍属于付过款。人工调账、赠送余额和兑换记录不能代替付款记录。邀请码用于注册，设置此条件会被拒绝。

兑换服务在锁定兑换码后、发放权益前，通过 app 注入的支付订单查询检查资格，查询使用兑换事务的连接。未付过款时返回 `REDEEM_PAYMENT_REQUIRED`；查询失败时返回服务端错误。两种情况均保持权益、使用次数和兑换记录不变，用户可以稍后重试。迁移 `287_redeem_code_requires_payment.sql` 为已有记录填入 `false`；所有服务实例升级后再开启该条件，因为旧二进制不会检查它。

代码原文是用户的凭据，查询和日志里都不暴露批量的未使用代码。已使用代码的类型、值、次数和套餐等核心字段，批量编辑时同样要通过一致性检查。支付充值生成的代码属于内部的履约实现，保持订单专属，并能识别部分执行后的重试。

管理员把余额设为某个值时，在同一条原子 SQL 里锁住并返回实际的旧值，调整量根据这个旧值计算，锁之前的快照不可靠。增加、减少、正数兑换的累计充值和普通加款，各有自己的处理规则。调账记录和返利尽力处理，这些后续步骤失败时，已经成功的充值不回滚。

## 领域不变量

- 外部的"成功"只有在验签、订单和实例绑定、金额校验全部通过后，才会产生权益。
- 订单保存下单时的商品和提供商快照；之后修改配置，历史订单的含义不变。
- 回调、查单、人工 retry 和后台 reconcile 使用同一个条件状态机和幂等履约入口。
- `COMPLETED` 表示内部权益已经发放；`PAID`、`RECHARGING`、`FAILED` 都还需要恢复处理。
- 订阅订单用 `source_order_id` 去重，余额订单用专属兑换码和它的使用记录去重；重复的通知不会重复加款或发放套餐。
- 低层额度只有在存在正数的外层有限额度时，才能在订阅尾段刷新；最高层额度和一次性的日额度跨窗口时不会重复发放。
- 周期额度负责拒绝新请求；已经成功完成的普通请求，即使最终费用超过剩余额度，也会正常收费：锁定订阅模式下超出部分记为余额欠费，订阅用量不超限；提交前的预占要求订阅完整覆盖金额。
- 取消、超时和退款不会覆盖同时发生的实际付款；状态不确定时，先向提供商查单。
- 权益变更后，让 Billing 和 API Key 认证缓存失效，并为状态、金额和操作者写审计记录。
