# 支付与权益

本文描述余额、订阅、兑换码和支付订单如何产生并撤销可消费权益。它用于修改支付或授权发放时保持金额、状态机和幂等不变量，不替代支付提供商接入参数、运营配置步骤或面向外部系统的接口手册。

## 权益模型

| 概念 | 作用 | 权威状态 |
| --- | --- | --- |
| 用户余额 | 没有适用订阅或订阅不足时承担网关消费 | 用户余额及其冻结金额，必须通过领域仓储原子调整 |
| `SubscriptionPlan` | 可售或可人工发放的权益模板 | 价格、币种、有效期、日/周/月额度、覆盖分组和分组倍率 |
| `UserSubscription` | 某用户实际拥有的带时间窗口权益 | 起止时间、active/pending/revoked 状态、额度快照、使用量和可选来源订单 |
| `RedeemCode` | 一次或有限次数的权益发放凭据 | 类型、值/套餐、有效期、最大次数、状态及用户兑换记录 |
| `PaymentOrder` | 外部资金事件与内部权益发放的协调记录 | 金额、币种/费用、订单类型、提供商与商品快照、状态、时间点和退款字段 |

billing 拥有余额原子调整、订阅/套餐及兑换规则；SQL/Ent 实现在 billing/postgres，相关 HTTP/DTO 在 billing/httpapi。payment 拥有支付配置、订单、渠道绑定、查单/履约和退款编排；promotion 拥有邀请码、返利和 Promo。旧聚合名称只作投影和委托，套餐规则仍由 billing 唯一拥有。用户/管理员套餐分别保持公开展示与历史 Ent JSON 形状。

订阅计划是可变商品配置，用户订阅才是已发放权益。购买订单保存计划快照，履约使用下单时的价格/权益语义，不能因管理员后来修改或删除套餐而改变已付款订单。余额订单与订阅订单共享支付确认流程，但进入不同履约分支。

## 订单与快照

创建订单前应完成用户归属、支付功能开关、订单类型、提供商实例、支付方式、币种、金额范围、套餐在售状态和促销规则校验。`out_trade_no` 是发给外部提供商的唯一商户订单号；本地数值 ID 只用于内部查找，旧版编号格式仅保留兼容回退。

订单持久化以下创建时事实：

- 应发权益金额 `amount`、实际支付金额 `pay_amount`、费用比例/固定费用及币种口径。
- `order_type`，以及订阅订单的 `plan_id` 与 `plan_snapshot`。
- `provider_instance_id`、`provider_key` 和 `provider_snapshot`，使回调、查单与退款仍使用原订单对应实例。
- 客户端来源、过期时间、外部 trade number、invoice/receipt 信息及完整状态时间点。

`payment.ConfigService`、`ProviderBindings` 和选择器由 app 唯一装配，具体渠道构造与密钥/环境投影不进入核心。首次实例读取失败不标记已加载；刷新先构造完整候选表再原子发布，整体读取失败保留旧表并允许重试，单个坏配置仍按原规则跳过。

提供商实例决定支持的支付类型、模式、限额、排序和退款能力。删除或修改当前实例不能把历史订单重新解释为另一个实例；解析旧订单时才允许按保存的 provider key 或兼容注册表回退。

## 支付状态机

正常成功路径为：

```text
PENDING -> PROCESSING -> PAID -> RECHARGING -> COMPLETED
    |          |            |          |
    |          +----------> EXPIRED    +-> FAILED -> retry
    +-> CANCELLED / EXPIRED
```

- `PENDING` 表示已创建且仍可由用户/管理员取消；外部报告处理中时用条件更新进入 `PROCESSING`。
- 支付成功先核对有限正数金额和币种最小单位容差，再从 `PENDING`、`PROCESSING`、`EXPIRED` 或 `CANCELLED` 恢复到 `PAID`。晚到成功不能因为本地超时而丢失真实付款。
- 履约通过条件更新获取有时限的 `RECHARGING` lease；只有 lease 持有者可以发放权益并进入 `COMPLETED`。
- 履约错误进入 `FAILED`，管理员或后台对账可以重试；卡住超过 lease 时限的 `RECHARGING` 也可被安全接管。
- 提供商明确失败可把尚未付款的 `PENDING/PROCESSING` 订单记为 `EXPIRED`。未知或不支持的回调状态不应猜测成功。

取消和过期不是简单的本地状态写入：订单已经关联外部支付时要先查单；如果提供商显示已付款或仍在处理，则不能把它覆盖成未付款终态。调用上游取消失败后需要再次查单，处理付款与关闭并发。所有状态迁移使用旧状态条件更新，竞争失败后重新读取当前状态并按实际终态返回。

<a id="forced_expiration_recovery"></a>
### 强制过期与失败退避

普通用户取消、管理员普通取消和后台超时关闭都保持 fail-closed：无法查询上游状态时，接口返回 `PAYMENT_STATUS_UNAVAILABLE`，订单继续为 `PENDING`，不能把可能已付款的订单直接关闭。失败首次写入 `PAYMENT_CANCEL_FAILED` 审计，并刷新订单 `updated_at`；超时 worker 仅在上次失败超过 15 分钟后重试，避免错误地址或暂时故障导致每分钟重复查单。

管理员可针对单笔 `PENDING` 订单调用强制过期操作，提交 1 至 500 个字符的原因。该操作不访问上游，在同一事务内使用条件更新写入 `EXPIRED` 并记录 `ORDER_FORCE_EXPIRED` 审计；审计写入或提交失败时必须整体回滚，状态已变化时返回冲突。它是明确的人工恢复手段，不替代普通取消或自动过期策略。有效的迟到付款通知仍可从 `EXPIRED` 进入 `PAID` 并按既有幂等履约流程处理。

存在仍为 `EXPIRED` 的 `ORDER_FORCE_EXPIRED` 订单时，原 provider instance 可以禁用，但不能硬删除。回调验证和迟到付款恢复仍需要该实例的历史凭据；订单恢复到非过期状态后，这项强制保留约束自动解除。

## 回调安全

Webhook 路由不依赖用户 JWT，因此提供商验签、订单绑定和金额验证构成授权边界：

1. 限制请求体大小，按提供商读取原始 body/query 和必要 header，不能先做会改变签名输入的重新序列化。
2. 尽可能从商户订单号找到原订单的具体 provider instance；多实例无法预判时逐个候选验签，只有成功验签的实例可以解释通知。
3. 验证 provider 自身签名、时间戳/重放窗口和事件类型，再验证通知中的 provider、trade number、订单 metadata 与本地快照一致。
4. 核对通知金额为有限正数且与订单 `pay_amount` 在币种容差内一致，之后才允许进入 `PAID`。
5. 不相关事件返回提供商要求的成功响应；验签或处理失败返回失败以便重试。确实不存在的本地订单可确认接收以阻止无意义重试，但必须留下告警。

回调是主要信号，主动 verify/查单和后台 reconcile 是漏回调、弹窗支付或进程中断后的恢复路径。它们必须复用同一状态迁移和履约函数，不能另写一套直接加余额逻辑。

## 履约与幂等

余额订单通过订单专属 `recharge_code` 复用兑换领域的原子权益调整：代码不存在时创建，存在但未使用时继续兑换，已经使用时只补齐后续步骤。订单级返利有自己的审计去重，兑换层在该路径跳过重复返利。只有权益与适用返利完成后，持有 lease 的调用者才能条件更新到 `COMPLETED`。

订阅订单调用 `AssignOrExtendSubscription`，把 `source_order_id` 设为订单 ID。服务在事务中锁定用户行后再次查询来源订单和最新同套餐订阅，使同一用户的并发发放先串行再扩展时间链；已有来源订单订阅则直接复用，因此 webhook、查单、人工 retry 和后台 reconcile 不会为同一订单重复发放。当前同套餐尚未过期时，新订阅从上一份 `expires_at` 开始并进入 `pending`，而不是覆盖或并行消耗。

`payment.OrderExpiry` 的 Start/Stop 幂等，停止不可逆；运行 context 贯穿锁、查询与渠道请求，取消后不进入下一项或阶段。app 保持立即首轮、原周期和 leader key/Redis→数据库回退，后台总预算 30 秒，超时不等于排空成功。

支付审计日志记录下单后的重要动作、operator 和详情。通知邮件等副作用在完成后异步派发，失败不能回滚已发权益；需要凭订单完成状态和审计动作避免重复通知。

## 退款

退款只从允许的已完成余额订单及配置为可退款的 provider instance 发起，用户自助退款还要满足实例 `allow_user_refund` 和业务资格。退款状态族包括 `REFUND_REQUESTED`、`REFUNDING`、`REFUND_PENDING`、`PARTIALLY_REFUNDED`、`REFUNDED` 和 `REFUND_FAILED`。

`payment.RefundWorkflow` 协调 `payment/postgres.RefundStore` 的短事务，通过 app 注入 billing 的原 Ent 同连接参与能力。退款仍先扣权益，明确失败或待确认时补偿；渠道调用不持数据库事务。

1. 准备事务锁定并认领订单，写实际预扣和 `REFUND_PREPARED` 恢复记录。记录有格式版本、本地操作标识、订单版本、扣减意图/实际值及订阅信息；任一步失败整体回滚，不调用渠道。
2. 渠道在事务外执行。Stripe 仍用订单号与最小货币单位退款额组成原幂等键，本地操作标识不参与渠道编码。
3. 明确失败或 pending 的补偿、订单状态和必要审计同事务提交。补偿或审计失败保留准备扣减和 `REFUNDING`，返回错误，不能按已成功补偿处理。
4. 即时成功只提交成功状态和成功审计，不再次扣减。该事务失败时外部退款可能已经完成，本地保留准备事实并返回错误。
5. pending 最终成功在同一事务内复核认领状态、版本及退款身份，再回收权益、更新状态和写成功审计。迟到失败不能覆盖较新的成功结果。

原管理员退款查单入口也接受有有效恢复记录的 `REFUNDING`，只查已发生的渠道操作并幂等完成，不重新发起退款。旧 `REFUND_PENDING` 字段继续兼容；缺失、损坏或矛盾的恢复资料，以及不支持渠道查单或结果不明时，明确要求人工核实，不能按默认零扣减完成。普通支付过程审计仍尽力写入，退款正确性依赖的记录必须持久化。原 `(order_id, action)` 唯一索引不变：同一动作的后续尝试更新当前版本，并将旧详情原样归档到 `history`，记录操作标识与时间，不能删除旧退款事实。旧 pending 中显式 `deductBalance=false` 保持其优先级，不能把“缺少该字段”解释为同一个意思。

回退到不识别准备记录的旧版本前，必须先处理或登记未完成退款；不得删除这些事实后盲目重试。

余额退款在非强制模式下发现余额不足时返回 `require_force`，只有管理员明确确认后才允许继续；强制退款也只能原子扣除当时可用的非负余额，并将实际扣减额写入结果和审计。订阅相关退款需要识别由 `source_order_id` 发放的订阅及其 active/pending 状态。强制退款属于明确的管理员操作，必须审计其理由，不能成为普通错误恢复路径。首次尝试返回 `require_force` 时，管理端保持退款弹窗、展示服务端警告，并且只有管理员显式勾选强制确认后才能携带 `force` 重试；关闭或重新打开弹窗必须清除上一次确认状态。

## 订阅生命周期

用户订阅复制发放时的有效期和日/周/月额度。状态语义为：当前开始时间已到的有效记录为 `active`，未来排队记录为 `pending`，人工撤销为 `revoked`；软删除也按 revoked 处理。是否可消费还要求当前时间落在 `[starts_at, expires_at)`、所有已配置的有限额度窗口均未耗尽，并满足套餐分组范围。

套餐分组为空表示该套餐不限制分组；非空时表示可消费的显式集合。用户的订阅列表响应以 `groups_restricted` 和带名称的 `applicable_groups` 展示这一区别。只有 API Key 显式选择该订阅时，才把 Key 的可选分组收窄到用户原有权限与该集合的交集；自动结算和仅余额 Key 不因用户持有受限套餐而被全局收窄。指定订阅的付款主体仍按 Key 归属解析，团队 Key 使用 Team Owner 的订阅权益。

<a id="subscription_quota_windows"></a>
### 周期额度窗口

周期额度有各自窗口起点和累计值，重置服务按项目时区推进窗口。日额度按日历日对齐，每天 0 点刷新；激活或手动重置写入当天 0 点，历史遗留的非零点锚点也会在下一个 0 点后自愈并写回当天 0 点。周/月额度继续按 7 天和 30 天窗口推进。到期尾段采用“日 < 周 < 月”的有限外层额度保护：日窗口若配置了正数周额度或月额度，即使订阅剩余时间不足 24 小时也可以刷新；周窗口若配置了正数月额度，即使剩余时间不足 7 天也可以刷新；月窗口没有更高层保护，仍须保证订阅剩余时间能容纳完整的 30 天窗口。未配置、零值或负数额度表示无限，不能充当尾段保护层；有效期不超过 1 天的日额度始终是一次性额度，不因外层额度而二次刷新。

事务结算会把订阅承担的消费同时累计到所有已配置的有限窗口，因此低层尾段刷新只恢复短周期可用量，外层累计值仍是新请求的硬性准入上限。普通请求通过预检并成功完成后，如果最终费用跨过指定订阅的剩余额度，事务必须把订阅用量封顶在可用额度，并将未覆盖的基础用量按余额倍率扣入付款主体余额，余额不足时允许形成负数欠费；不能因严格封顶导致结算回滚和零计费。该欠费只用于结算已经放行或并发在途的请求，不赋予额外权益，后续绑定该订阅的新请求仍按 `used >= limit` 拒绝，不因余额可用而自动回退。批量任务在提交上游前的额度预占不适用该例外，指定订阅无法完整覆盖时必须回滚并拒绝。服务层预检、额度进度展示和数据库事务归一化必须使用同一套尾段规则，不能让缓存判断与最终扣费出现分叉。结算在数据库事务中锁定并累计当前使用；读取缓存仅用于热路径预检，提交后的缓存与认证失效按各入口现有顺序执行；当前 `InvalidateSubCache` 是空兼容入口，不能把它作为有效广播或跨实例失效证据。

同用户同套餐的连续订阅形成时间链。管理延长、撤销、有效期调整及重置在事务内先锁用户，再读取最新订阅和时间链；两个并发延长必须累加，不能用旧快照覆盖。有效期调整参加已有外层事务，外层回滚时全部撤销。延长或调整有效期需要保持后续 pending 记录不重叠；恢复已撤销记录也要重新计算插入位置。`source_order_id` 是支付发放幂等键，人工发放、默认注册发放和兑换码发放没有来源订单时使用各自的事务/锁边界。

<a id="subscription_self_revoke"></a>
用户自助撤销只允许作用于本人当前 `active` 订阅，且只在最高层已配置的正数有限额度耗尽时开放：优先检查月额度，其次周额度，最后日额度；低层窗口暂时耗尽或套餐没有有限额度都不能撤销。`POST /api/v1/subscriptions/:id/revoke` 在同一事务中复核状态和额度、软删除当前记录并平移后续同套餐链；第一份 pending 因此立即生效。若存在接续记录，所有 `billing_mode=subscription` 且显式绑定旧订阅 ID 的个人、团队、复合和托管 API Key 一并改绑到接续记录；没有接续记录时保留旧绑定并使其不可用。该操作不退款，用户不能自行恢复。

订阅过期与 7/3/1 天提醒由 billing 的维护器扫描，邮件模板、收件人处理和投递仍委托旧通知能力。app 注入时钟、独立操作预算和既有 leader 锁策略，构造期间不启动任务。

## 兑换码

兑换码可发余额、并发或订阅权益，邀请码不从用户兑换入口产生权益。服务先做用户失败次数限制，再以代码级短期锁串行化请求；仓储在事务内锁定代码、校验状态/有效期/最大使用次数和“同用户一次”记录，并原子写入权益调整与使用记录。

代码原文是用户凭据，查询或日志不能泄露批量未使用代码。已使用代码的类型、值、次数和套餐等核心字段不可通过批量编辑绕过一致性检查。支付充值生成的代码属于内部履约实现，必须保持订单专属且可识别部分执行后的重试。

管理员余额 set 在同一原子 SQL 中锁定并返回真实旧值；调整量不能从锁前快照推算。add/subtract、正数兑换累计充值和普通加款保留各自差异。调账记录及返利仍按原入口尽力处理，不因这些后置失败回滚已成功充值。

## 领域不变量

- 外部“成功”只有在验签、订单/实例绑定和金额校验全部通过后才能产生权益。
- 订单保存下单时商品和提供商快照；后来修改配置不能改变历史订单语义。
- 所有回调、查单、人工 retry 和后台 reconcile 复用同一条件状态机与幂等履约入口。
- `COMPLETED` 表示内部权益已经发放，不仅表示提供商已收款；`PAID/RECHARGING/FAILED` 都仍需恢复处理。
- 订阅订单用 `source_order_id` 去重，余额订单用专属兑换码与 usage 去重；重复通知不能重复加款或发套餐。
- 低层额度只有在存在正数有限外层额度时才可于订阅尾段刷新；最高层额度和一次性日额度不得因跨窗口边界重复发放。
- 周期额度负责阻止新请求，不得让已经成功完成的普通请求因最终费用跨过剩余额度而免费；锁定订阅模式的溢出部分必须形成余额欠费，订阅用量不得超限，提交前预占仍须严格受限。
- 取消、超时和退款不能覆盖并发发生的真实付款，所有不确定状态优先查提供商而不是猜测。
- 权益变更后同步失效 Billing/API Key 认证缓存，并为状态、金额和操作者写审计记录。
