## 权益模型

| 概念 | 作用 | 状态保存在哪里 |
| --- | --- | --- |
| 用户余额 | 没有适用订阅或订阅不足时承担网关消费 | 用户余额和冻结金额，通过领域仓储原子调整 |
| `SubscriptionPlan` | 可出售或人工发放的权益模板 | 价格、币种、有效期、日/周/月额度、覆盖分组和分组倍率 |
| `UserSubscription` | 用户实际拥有的带时间窗口权益 | 起止时间、`active`/`pending`/`revoked` 状态、额度快照、用量和可选来源订单 |
| `RedeemCode` | 单次或有限次使用的权益凭据 | 类型、值或套餐、有效期、最大次数、状态和用户兑换记录 |
| `PaymentOrder` | 外部资金事件与内部权益发放的协调记录 | 金额、币种和费用、订单类型、提供商与商品快照、状态、时间点和退款字段 |

各模块职责如下：

- `billing`：维护余额原子调整、订阅、套餐和兑换规则（`billing/postgres` 负责存储，`billing/httpapi` 负责接口）。套餐规则仅在此处维护，用户端与管理端套餐接口分别保持公开展示格式和历史 Ent JSON 格式。
- `payment`：维护支付配置、订单、渠道绑定、查单、履约和退款编排，直接调用 `billing` 权益接口。
- `promotion`：维护邀请码、返利和 Promo，直接调用 `billing` 权益接口。

订阅计划是可修改的商品配置，用户订阅才是已发放权益。购买订单保存计划快照，履约按下单时的价格和权益执行；后续修改或删除套餐不影响已付款订单。余额和订阅订单共用支付确认流程，确认后进入各自履约分支。

## 订单与快照

创建订单前依次校验：

1. 用户归属与支付功能开关。
2. 订单类型、提供商实例、支付方式和币种。
3. 金额范围、套餐是否在售以及促销规则。

商户订单号规则：

- `out_trade_no` 是发给外部提供商的唯一商户订单号，新订单格式为 `tr_` + 日期 `YYYYMMDD` + 8 位随机字母数字；本地数值 ID 仅用于内部查找。
- 查单和回调按完整 `out_trade_no` 匹配。未命中时，历史 `sub2_<本地订单 ID>` 格式可回退按数值 ID 查找；`tr_` 订单号只按完整值查询。

订单持久化以下下单快照：

- 金额与费用：应发权益金额 `amount`、实付金额 `pay_amount`、费率、固定费用和币种。
- 商品快照：`order_type`，以及订阅订单的 `plan_id` 和 `plan_snapshot`（含下单语言、当时展示的套餐名称和商品名称）。
- 渠道快照：`provider_instance_id`、`provider_key`、`provider_snapshot`，以及固定渠道商品描述的 `display_locale`、`display_subject`。回调、查单和退款使用订单当时的实例。
- 过程记录：客户端来源、过期时间、外部 trade number、invoice、receipt 和每次状态变更时间点。

提供商实例运行约束：

- 渠道构造、密钥和环境信息留在渠道适配层。首次读取实例失败时不标记为已加载；刷新先构造完整候选表再原子发布，整体读取失败时保留旧表并允许重试，单个损坏配置跳过。
- 提供商实例决定支持的支付类型、模式、限额、排序和退款能力。修改或删除当前实例后，历史订单仍按原实例解释；仅解析旧订单时按保存的 `provider_key` 或兼容注册表回退。

套餐介绍、权益、支付帮助和自定义方式名称的翻译规则见[用户侧国际化](../interfaces/user_localization.md#content_owners)。

<a id="personal_recharge_multiplier"></a>
## 用户专属充值倍率

管理员可为用户设置 `balance_recharge_multiplier`，有限正数覆盖全局余额充值倍率（允许低于或等于全局值），`NULL` 跟随全局设置。该字段属账户支付条款，普通用户不能通过资料接口修改；管理员编辑时省略该字段保留原值，显式提交 `null` 清除覆盖。

计算与校验规则：

- 共享规则：充值页预览和新余额订单共用同一倍率选择规则。读取用户覆盖值失败时直接返回错误，不能用全局倍率替代。
- 到账计算：到账金额等于本金乘以实际倍率，前后端均按十进制乘法四舍五入保留两位小数。手续费、充值限额、订阅购买、兑换码和人工调账沿用各自原规则。
- 订单类型：新订单只接受 `balance` 或 `subscription`，省略时默认 `balance`，其他值在下单前拒绝。
- 金额范围：余额到账金额舍入后必须满足 `>= 0.01` 且 `< 1 万亿`（匹配兑换码和钱包的 `numeric(20,8)` 上限）。不合法时在保存订单和调用渠道前返回 `INVALID_CREDITED_AMOUNT`，前端禁用支付按钮并提示调整金额。倍率配置本身仍接受任意有限正数。

快照与展示规则：

- 订单 `amount` 固化下单时的到账金额，后续全局或用户倍率变更不修改该快照；履约、重复回调和按比例退款均读取订单金额。
- 专属倍率为 1 时，充值页仍展示到账金额和倍率说明；与全局倍率相同时只强调专属值，不重复划掉相同数字。
- 管理列表专属倍率列仅展示覆盖值，在分页前按数值排序，升序和降序均将 `NULL` 排在末尾。

接口字段见[用户专属充值倍率接口](../interfaces/http_api.md#personal_recharge_multiplier_api)。

<a id="payment_statistics_units"></a>
## 支付统计与展示单位

账户到账金额、余额和订阅额度使用配置的自定义余额单位；实付金额使用订单保存的支付币种。支付仪表盘按币种分别汇总收入、购买分布和平均购买单价。

- 购买分布：`purchase_distribution` 每条记录带有 `currency`，同一套餐或按量支付类别在不同币种下独立统计；前端先选择币种，再计算该币种内的金额和订单数占比。
- 订阅订单双币种：订阅订单的 `amount` 为原始套餐价格，`amount_currency` 来自下单时的套餐快照；`pay_amount` 和手续费使用支付通道 `currency`。创建订单、用户查询、公开支付结果和管理员查询均返回这两个币种，页面分别格式化原价和实付。
- 余额与历史兼容：余额订单省略 `amount_currency`，到账数量使用自定义余额单位。启用 USD 到 CNY 换算时，未填币种的套餐在快照中记为 `USD`；历史快照无可用套餐币种时，原价展示沿用订单支付币种。
- 平均购买单价：`avg_reasoning_point_purchase_unit_price` 返回币种到单价的映射，按该币种 `本金合计 / 购买单位合计` 保留四位小数。
- 统计口径与展示：本金为实付减手续费，购买单位取余额订单到账金额或订阅快照月额度，非正值不参与。`reasoning_point_purchase_order_count` 为全币种参与总数，展示格式为"支付币种 单价/自定义余额单位"。

## 支付状态机

正常成功路径与分支：

```text
PENDING -> PROCESSING -> PAID -> RECHARGING -> COMPLETED
    |          |            |          |
    |          +----------> EXPIRED    +-> FAILED -> retry
    +-> CANCELLED / EXPIRED
```

| 状态 | 含义与迁移规则 |
| --- | --- |
| `PENDING` | 订单已创建，用户或管理员可取消；上游报告处理中时通过条件更新进入 `PROCESSING` |
| `PAID` | 支付成功前先核对金额为有限正数且在币种最小单位容差内，允许从 `PENDING`、`PROCESSING`、`EXPIRED` 或 `CANCELLED` 迁入，避免晚到成功丢单 |
| `RECHARGING` | 履约通过条件更新获取有时限 lease，仅 lease 持有者发放权益并进入 `COMPLETED`；超出 lease 时限后可安全接管 |
| `FAILED` | 履约出错转入，可由管理员或后台对账重试 |
| `EXPIRED` | 提供商明确失败时，未付款的 `PENDING` 或 `PROCESSING` 记为 `EXPIRED`；未知或不支持回调状态按未确认处理 |

防覆盖与并发保护：

- 已关联外部支付的订单在取消或过期前先向上游查单；上游显示已付款或处理中时保持当前状态。
- 调用上游取消失败后再查一次单，处理付款与关闭并发的情况。
- 所有状态迁移均以旧状态为条件更新；竞争失败后重读当前状态，按实际终态返回。

<a id="forced_expiration_recovery"></a>
### 强制过期与失败退避

用户取消、管理员普通取消和后台超时关闭均采用 fail-closed 策略：

- 查不到上游状态时返回 `PAYMENT_STATUS_UNAVAILABLE`，订单保持 `PENDING`，避免误关可能已付款的订单。
- 首次失败写入 `PAYMENT_CANCEL_FAILED` 审计并刷新订单 `updated_at`；超时 worker 在上次失败超过 15 分钟后才重试，避免持续高频查单。

管理员手动强制过期规则：

- 仅针对单笔 `PENDING` 订单，需填写 1 到 500 字符原因。
- 不访问上游，在同一事务内条件更新为 `EXPIRED` 并写入 `ORDER_FORCE_EXPIRED` 审计；审计或提交失败整体回滚，状态已变时返回冲突。
- 有效迟到付款通知仍可将订单从 `EXPIRED` 带入 `PAID` 并走幂等履约。
- 存在 `EXPIRED` 状态的 `ORDER_FORCE_EXPIRED` 订单时，对应 provider instance 可禁用但不可硬删除，用于保留回调验签和迟到付款恢复凭据；订单离开过期状态后该限制自动解除。

<a id="callback_security"></a>
## 回调安全

Webhook 路由不使用用户 JWT，依靠提供商验签、订单绑定和金额核对完成授权：

1. 限制请求体大小，按提供商要求读取原始 body、query 和必要 header，验签前不重新序列化。
2. 尽量从商户订单号定位原订单对应的 provider instance；无法预判时逐个实例尝试验签，仅验签成功的实例可解释该通知。
3. 校验签名、时间戳和重放窗口、事件类型，再核对通知中的 provider、trade number 和 metadata 与本地快照一致。
4. 核对通知金额为有限正数且与订单 `pay_amount` 在币种容差内一致后，再迁入 `PAID`。
5. 无关事件按提供商要求返回成功；验签或处理失败返回失败以触发重试。本地确实不存在的订单可确认接收并记告警，停止无效重试。

### 易支付（EasyPay）验签、兼容与查单

易支付 MD5 协议直接拼接参数值，浏览器下单 URL 带有签名。`EasyPay.VerifyNotification` 验签前执行严格校验：

- 字段白名单：仅允许 `pid`、`trade_no`、`out_trade_no`、`type`、`name`、`money`、`trade_status`、`param`、`sign`、`sign_type`，以及 V1 扩展字段 `api_trade_no`、`addtime`、`endtime`、`buyer`、`timestamp`。白名单外字段和重复字段均拒绝，空值字段同样参与检查。
- 内容校验：`pid`、`trade_no`、`out_trade_no`、`type`、`money`、`trade_status` 必须非空；除自由文本的商品名外，其余字段（含可选字段和 `param`）含 `&`、`=`、控制字符或首尾空白时拒绝。
- 格式与解码：`type` 仅允许小写字母、数字、下划线和连字符，`pid` 须匹配验签实例，`money` 须为有限正数；所有参数按协议解码一次后验签。
- 二次查单：成功通知用验签的同一商户实例按 `out_trade_no` 查单，确认已支付、金额按 CNY 分一致且交易号相同，再与本地订单快照核对商户、金额和已有交易号。

商户订单号回显兼容（`allowMerchantOrderNoAsTradeNo`）：

- 该配置默认关闭，管理员创建、编辑和适配器构造仅接受空值、`"true"`、`"false"`（前端关闭时显式提交 `"false"`）。读取订单绑定实例的当前配置，同样适用于历史未确认付款订单。
- 开启后，若下单响应的 `trade_no` 精确等于本次 `out_trade_no`，适配器将支付交易号留空等待首次付款确认。历史订单已保存回显值时，仅允许无 `paid_at` 且状态为 `PENDING`、`PROCESSING`、`EXPIRED` 或 `CANCELLED` 的订单纠正。
- 已支付查单必须返回与请求一致的 `pid`、`out_trade_no`、有效金额和真实交易号，适配器据此生成绑定订单的内部确认标记（外部回调无法伪造）。回调仍需验签并与同商户查单金额和交易号一致，再核对本地金额；真实交易号与 `PAID` 状态一并条件更新，并发重读后再次检查。付款确认后，冲突交易号继续拒绝，余额与订阅沿用持久化幂等约束。

结果页与查单错误处理：

- 结果页地址：`CanonicalizeReturnURL` 拒绝 userinfo 及主机名中的 `&`、`=`，以校验后的 scheme、host 和 `/payment/result` 重建 URL，再拼接 `order_id`、`out_trade_no`、`resume_token` 和 `status`。参数仅用于找回和展示，确认依赖上游查单与回调验签。
- 统一入口：主动 verify、查单、后台 reconcile 与回调共用同一状态迁移和履约函数，加余额只在履约函数中发生。
- V1 查单兼容与脱敏：易支付查单在单次 POST 的 URL query 和表单中同时提交相同参数。传输失败输出固定错误文本，仅保留取消和超时标识，不把可能包含商户密钥的底层错误带入调用方错误链。
- 查单结果语义：HTTP 与业务状态均成功才解析订单；已支付需有效金额和真实交易号，返回的商户和订单号如存在须匹配。查单失败、未支付或字段冲突时拒绝成功通知待渠道重试。渠道明确返回订单不存在时：连接测试视为可达，取消和过期视为未付款（兼容未打开收银台的弹窗订单），成功回调仍拒绝。

<a id="epusdt_payments"></a>
## EPUSDT 加密货币支付（EPay 协议）

`epusdt` 接入 EPUSDT / GMPay 的 EPay（易支付）兼容协议，支持余额充值和订阅购买，不调用通用易支付的 `mapi.php` 或 `api.php`。

下单与签名：

- 向部署基础地址下的 `/payments/epay/v1/order/create-transaction/submit.php` POST 表单，`money` 为 CNY 或 USD 法币金额，`out_trade_no` 标识本地订单，固定提交 `type=alipay`。币种和网络由网关默认配置及托管收银台决定。
- MD5 签名按字段名排序，排除 `sign`、`sign_type` 和空值，拼接 `key=value` 后追加商户密钥。
- 仅接受同源 HTTPS 收银台跳转，从 `/pay/checkout-counter/{trade_id}` 提取保存交易号，不在后端跟随跳转。响应不含有效期，沿用本地下单截止时间。
- 发送给网关的商品名将 `&` 和 `=` 替换为全角字符，控制字符替换为空格并去首尾空白，避免触发回调校验拒绝；本地快照和页面展示保留原名称。

回调与主动查单：

- 回调接受 GET query 和 POST form，白名单为 `pid`、`out_trade_no`、`trade_no`、`money`、`type`、`trade_status`、`name`、`param`、`sign`、`sign_type`。重复字段、未知字段、含分隔符或控制字符的值（含商品名）在验签前拒绝。
- 付款确认要求 `pid`、MD5 签名、`type=alipay`、`trade_status=TRADE_SUCCESS`，并通过收银台状态接口二次核对已付款和法币金额；运行时再核对本地商户、币种、交易号和金额快照。
- 主动查单使用已保存 `trade_id`，经 HTTPS 读取 `/pay/checkout-counter-resp/{trade_id}`（金额与币种）和 `/pay/check-status/{trade_id}`（状态：1 和 4 为待付款，2 为已付，3 为过期，未知状态和查询失败保持未确认）。后台对账同样扫描未过期的 EPUSDT 待付款订单。

未确认恢复与失败边界：

- 创建请求不自动重试。传输失败、无法验证收银台跳转或响应资料落库失败时返回 `PAYMENT_CREATE_UNCONFIRMED`，保留待确认订单并向已认证购买者返回恢复信息，前端进入等待页。缺少 `trade_id` 时上游无按商户订单号查单接口，需等签名回调或人工核实，自动取消按查单失败处理。
- 上游明确拒绝创建时订单进入 `FAILED`，释放待付款额度和实例配置修改保护。明确拒绝仅限：HTTP 401 对应验签错误码 401，或 HTTP 400 对应已知金额、参数、回调地址、汇率、钱包、金额通道、链和币种校验错误，且响应不携带订单数据。重复订单、系统错误、未知错误码、损坏或截断响应仍按未确认处理。
- 存在未完成订单时，实例配置中的 PID、密钥、币种和 API 地址禁止修改。EPUSDT 自动退款在配置接口和适配器中均被拒绝；本地取消后，真实晚到成功通知仍可幂等履约。

## 履约与幂等

余额与订阅订单采用各自的幂等键，保证重复回调、主动查单、人工重试和后台对账不重复发放：

- 余额订单：通过订单专属 `recharge_code` 复用兑换的原子权益调整。代码不存在时创建，存在未使用时继续兑换，已使用时仅补完后续步骤。订单级返利有独立审计去重，兑换层在这条路径跳过返利。权益和返利均完成后，lease 持有者条件更新订单为 `COMPLETED`。
- 订阅订单：调用 `AssignOrExtendSubscription` 并写入 `source_order_id`。事务内先锁用户行，再查来源订单和同套餐最新订阅；已有该来源订单的订阅时直接复用。同套餐尚未过期时，新订阅从上一份的 `expires_at` 开始，状态为 `pending`，两份订阅按时间衔接。
- 过期扫描任务：`payment.OrderExpiry` 启动后立即执行首轮，之后按固定周期运行，执行前抢占任务锁（Redis 不可用时回退数据库），单轮总预算 30 秒（超时不代表已排空）。`Start` 和 `Stop` 可重复调用，停止后无法重启，context 取消后不再进入下一项或下一阶段。
- 审计与通知：审计记录下单后的重要动作、操作者和详情。通知邮件在完成后异步派发，发送失败不回滚已发放权益，通过完成状态和审计动作去重。

## 退款

| 发起角色 | 可退范围 | 金额与订阅处理 |
| --- | --- | --- |
| 用户自助 | 已完成的余额订单，且原支付实例开启用户退款 | 按余额订单规则退款 |
| 管理员 | 余额订单（支持一次部分退款）或订阅订单（仅全额退实付金额） | 退订阅时勾选「撤销订阅」立即暂停该订阅、渠道确认成功后撤销；取消勾选保留订阅 |

### 退款四步流程

资金与权益变更在短事务内原子完成，外部渠道请求放在事务外执行：

1. 准备事务：认领订单为 `REFUNDING`，锁定付款用户及来源订单订阅。余额订单记录实际预扣金额，订阅订单写入带本次操作 ID 的暂停标记；订单、权益变更与 `REFUND_PREPARED` 同时提交，任一步失败整体回滚且不请求渠道。
2. 调用渠道：收到渠道退款 ID 先写回准备凭据。Stripe 按订单号和最小货币单位金额设幂等键；Stripe 返回结果未知时保留 `REFUNDING` 和准备凭据。
3. 处理中状态：渠道报告处理中时订单进入 `REFUND_PENDING`。余额预扣按原金额退回余额（累计充值不变）；订阅保留暂停标记，网关准入、资金分配和新任务预占均排除它，后续订阅仍按原时间排队。
4. 确认与补偿：渠道确认成功时在单事务内核对操作身份、完成权益回收（订阅撤销与续订调整同步提交）并写成功审计。明确失败时解除该操作的订阅暂停。补偿事务使用独立限时上下文，管理端断连仍可完成；有效期和用量按原规则计算，已自然过期的订阅仍为过期。

### 渠道响应与补偿判定

| 渠道 | 确认成功条件 | 允许自动补偿的明确拒绝 | 结果未知处理 |
| --- | --- | --- | --- |
| 易支付（EasyPay） | 完整匹配 JSON `code=1`、`code=0` 配明确退款成功消息，或"退款成功"纯文本及金额后缀（含金额须匹配本次 CNY 金额）；"退款申请成功"、矛盾或残缺响应不确认 | 完整匹配已知业务拒绝（如余额不足、权限不足、参数错误）；仅明确业务订单不存在时允许换另一订单标识重试 | `SYSTEMERROR`、`ACQ.SYSTEM_ERROR`、"系统错误"、未识别文案、超时或断连返回 `ErrRefundOutcomeUnknown`，保留扣减、`REFUNDING` 与 `REFUND_PREPARED`，接口返回 `REFUND_RECOVERY_REQUIRED` |
| Airwallex | 渠道确认退款成功 | 参数校验失败、找不到支付交易、金额超限、权限不足 | 无法确认受理的 HTTP 错误和断连保留恢复记录 |
| Stripe | 渠道确认退款成功 | 渠道明确拒绝 | 保留 `REFUNDING` 和准备凭据，走退款查单或补录 ID |

易支付处于 `REFUND_RECOVERY_REQUIRED` 时，管理端关闭弹窗、刷新状态并提示到支付平台核实，禁止重发退款。EasyPay V1 不支持退款查单，普通支付查单不能证明退款完成，需人工核对外部结果和准备记录；历史上外部成功却已在本地补偿的订单需逐笔对账，升级不自动修复。

### 退款查单、恢复记录与强制确认

- 查单入口：管理员查单仅接受带有效恢复记录的 `REFUNDING` 和 `REFUND_PENDING` 订单，只查询已提交的渠道操作。
- Stripe 查单与补录：优先按已保存退款 ID 核对支付意图、币种和金额；无退款 ID 时，自动查单仅接受从准备时间起唯一匹配且已成功的退款。自动查单无法确认的 `REFUNDING` 订单支持补录 Stripe 退款 ID，核验支付意图、币种、金额和创建时间后保存并推进状态，已保存 ID 禁止替换。
- 历史凭据与人工核实：旧退款凭据仍可读。历史订阅预扣记录显示补偿失败时，仅在渠道确认成功且原订阅已撤销时补齐订单状态；渠道明确失败时按原订阅和续订链人工恢复。恢复资料缺失、损坏、矛盾，或渠道不支持查单/结果不明确时要求人工核实，不假设扣减为零自动完成。
- 审计持久化与版本：退款关键记录必须持久化（普通支付审计尽力写入）。`(order_id, action)` 唯一索引不变，后续尝试更新当前版本并将旧详情（含操作标识与时间）归档至 `history`。旧 pending 记录显式 `deductBalance=false` 时优先遵守；降级至不识别准备记录的版本前，须先处理或登记未完成退款。
- 强制退款（`require_force`）：余额不足或撤销已过期、已撤销、不存在的原订阅时，须管理员填写理由并显式带 `force` 重试（订阅读取错误中止准备事务）。强制退款仍只原子扣除可用非负余额并记录实际扣减额；管理端收到 `require_force` 后保持弹窗并提示警告，关闭或重开弹窗清除确认状态。

## 订阅生命周期

用户订阅复制发放时的有效期和日、周、月额度。

- 状态定义：开始时间已到的有效记录为 `active`，未来排队为 `pending`，人工撤销或软删除为 `revoked`，退款暂停且未过期的原订阅显示为 `suspended`。
- 消费条件：当前时间在 `[starts_at, expires_at)` 内、所有有限额度窗口均有余量，且请求属于套餐覆盖分组。
- 分组覆盖：套餐分组为空不限分组，非空限定允许消费的分组集合，列表以 `groups_restricted` 和带名称的 `applicable_groups` 展示。仅 API Key 显式绑定订阅时，可选分组收窄为用户权限与套餐集合的交集（团队 Key 用 Team Owner 订阅）；自动结算和只用余额的 Key 保持原范围。
- 已删除分组兼容：保存套餐时核验 `group_ids` 仍存在，指向已删除分组返回 `GROUP_NOT_FOUND` 不落库。删除分组只清理分组授权和提供商关联，不删套餐里的旧 ID；订阅列表读取时过滤确认已删除的分组（查询失败保留仅 ID 条目），管理端编辑套餐时丢弃已删除分组及倍率覆盖并在保存时修正。不带 `group_ids` 的部分更新保留原分组选择，不做分组查询。

<a id="subscription_quota_windows"></a>
### 周期额度窗口

各周期额度维护独立的窗口起点和累计值，重置服务按项目时区推进：

| 周期窗口 | 对齐与推进规则 | 尾段刷新保护（日 < 周 < 月） |
| --- | --- | --- |
| 日额度 | 按项目时区日历日 0 点刷新；激活或手动重置写当天 0 点，历史非零点起点在下一个 0 点后自动修正 | 配置正数周额度或月额度时，剩余不足 24 小时仍可刷新；有效期不超过 1 天的订阅，日额度始终一次性 |
| 周额度 | 按 7 天窗口推进 | 配置正数月额度时，剩余不足 7 天仍可刷新 |
| 月额度 | 按 30 天窗口推进 | 无更高层保护，订阅剩余时间须能容纳完整 30 天窗口 |

未配置、为零或为负的额度表示无限，不提供外层保护。

结算、超额封顶与时间链规则：

- 多层累计：事务结算将订阅消费同时累计到所有已配置的有限窗口，低层尾段刷新只恢复短周期可用量，外层累计值仍是新请求的硬准入上限。
- 普通请求超额封顶：预检放行并成功完成后，若最终费用超出指定订阅剩余额度，事务将订阅用量封顶在可用额度，超出基础用量按余额倍率从付款主体余额扣除（余额不足可为负数欠费）。该欠费仅结算已放行或在途并发请求，之后绑定该订阅的新请求仍按 `used >= limit` 拒绝（即使余额充足）。
- 批量任务预占例外：批量任务提交上游前的额度预占不适用上述封顶，指定订阅无法完整覆盖时回滚并拒绝。
- 规则一致与缓存：预检、额度进度展示、数据库事务归一化和任务预占取消退回（1 日历日、7 天、30 天窗口）共用同一时区和尾段规则。结算在数据库事务内锁定累计用量，读缓存仅用于热路径预检，提交后按各入口顺序失效缓存和认证；`InvalidateSubCache` 目前为空兼容入口。
- 时间链并发：同用户同套餐连续订阅构成时间链。管理端延长、撤销、有效期调整和重置均在事务内先锁用户再读最新链；并发延长累加不覆盖，有效期调整加入外层事务随外层回滚；调整或恢复撤销记录时保持后续 `pending` 不重叠并重算链位置。`source_order_id` 是支付发放幂等键；人工、注册默认和兑换码发放各自通过事务和锁防重。

<a id="subscription_self_revoke"></a>
### 用户自助撤销

用户仅可撤销本人当前 `active` 订阅，且仅在最高层已配置的正数有限额度用完时开放（按月 > 周 > 日判断）。仅低层窗口用完或套餐无有限额度时不可撤销。

- 事务动作：`POST /api/v1/subscriptions/:id/revoke` 同事务复核状态和额度，软删除当前记录并将同套餐后续链前移，使第一份 `pending` 立即生效。
- Key 改绑：存在接续订阅时，所有 `billing_mode=subscription` 且绑定旧订阅 ID 的个人、团队、复合和托管 API Key 一起改绑到接续订阅；无接续时旧绑定不变，这些 Key 不可用。撤销不退款，用户无法自助恢复。
- 到期提醒：订阅过期及到期前 7、3、1 天提醒由 `billing` 扫描，邮件模板、收件人和投递归 `notification`，见[通知与邮件投递](notification_delivery.md)。

<a id="redeem_eligibility"></a>
## 兑换码

自定义长度与搜索：

- 管理员自定义兑换码最多 32 个 Unicode 码点（常用汉字、生僻汉字和英文字母各计 1，数据库 `VARCHAR(32)`）。前端提交、生成接口、管理服务和 Ent 写入均按码点限长。
- 前端和管理服务创建前去除首尾空白；前端超长时提示修改并保留输入内容。列表和导出搜索词去首尾空白并截取前 100 个码点。

兑换规则与有效期：

- 兑换码可发放余额、并发或订阅权益；邀请码不能走用户兑换入口。
- 订阅码 `validity_days` 非空时固定发放该天数（范围 1 至 36500），`NULL` 使用兑换时套餐默认有效期；该字段与控制兑换期限的 `expires_at` 独立，套餐额度模板在兑换时读取。
- 兑换先限制用户失败次数，再用代码级短期锁排队；仓储在事务内锁代码，核验状态、有效期、最大使用次数和单用户限用一次，原子写入权益和使用记录。

付费门槛（`requires_payment`）：

- 创建或单条编辑余额、并发、订阅兑换码时可开启（默认关闭）；邀请码设置此条件会被拒绝。
- 开启后，领取者须有至少一笔本人支付订单满足 `paid_at` 已写入且 `pay_amount > 0`（金额不限）。后续履约失败或退款仍算付过款；人工调账、赠送余额和兑换记录不能替代。
- 兑换服务在锁码后、发放权益前于同一兑换事务内检查资格：未付款返回 `REDEEM_PAYMENT_REQUIRED`，查询失败返回服务端错误；两种情况均保持权益、次数和记录不变，允许稍后重试。
- 升级注意：迁移 `287_redeem_code_requires_payment.sql` 为存量记录填充 `false`；须在所有实例升级后再开启该条件，旧版本不执行此校验。

凭据安全、调账与插件签发：

- 代码原文是用户凭据，查询和日志不批量暴露未使用代码。批量编辑时对已使用代码的类型、值、次数和套餐等核心字段执行一致性检查。支付充值生成的内部兑换码保持订单专属，支持部分执行后重试。
- 管理员设定余额在单条原子 SQL 中锁定并返回实际旧值计算调整量；增加、减少、正数兑换累计充值和普通加款各按规则处理；调账记录和返利尽力执行，失败不回滚已成功充值。
- 插件签发的兑换码固定单次使用，订阅天数在发码事务中按已授权额度校验并保存（`validity_days=0` 先折算当时套餐默认值存为正天数）；余额码兑换沿用普通累计充值和返利规则。
- 插件直接余额调整记为 `plugin_balance` 历史类型（备注带插件 ID），操作与幂等台账同事务提交，缓存清除和历史记录在提交后执行；加款不计入累计充值，不走直接充值返利。授权与额度规则见[插件写能力](../architecture/plugin_system.md#write_capabilities)。

## 领域不变量

- 外部成功信号只有在验签、订单与实例绑定、金额校验全部通过后，才会产生权益。
- 订单保存下单时的商品和提供商快照，后续配置变更不改变历史订单含义。
- 回调、查单、人工 retry 和后台 reconcile 共用同一条件状态机和幂等履约入口。
- `COMPLETED` 表示内部权益已发放；`PAID`、`RECHARGING`、`FAILED` 仍需恢复处理。
- 订阅订单以 `source_order_id` 去重，余额订单以专属兑换码及使用记录去重，重复通知不重复发放。
- 低层额度仅在存在正数外层有限额度时允许在订阅尾段刷新；最高层额度和一次性日额度跨窗口不重复发放。
- 周期额度拒绝新请求；已成功完成的普通请求若超出剩余额度，锁定订阅模式下超出部分记为余额欠费且订阅用量不超限，提交前预占则要求订阅完整覆盖。
- 取消、超时和退款不覆盖并发发生的实际付款；状态不确定时先向上游查单。
- 权益变更后失效 Billing 与 API Key 认证缓存，并为状态、金额和操作者写入审计记录。
