## 资源关系

| 资源 | 职责 | 主要关系 |
| --- | --- | --- |
| API Key | 客户端凭据和消费单位 | 属于付款用户，可以属于团队；普通 Key 指向一个分组，复合 Key 通过前缀映射到多个分组；结算来源可以选自动、指定订阅或只用余额 |
| Group | 面向用户的产品和策略单位 | 规定公开或独占、倍率、客户端协议、回退目标、模型规则、RPM 和展示策略；可以关联不同平台的提供商 |
| PricingConfig | 多个分组共享的价格配置 | 一个分组最多关联一个配置；按模型、计费方式、区间和计费来源解析价格，不区分平台 |
| Provider | 实际调用上游的凭据和运行资源 | 通过多对多关系加入分组；保存平台、凭据、代理、并发、优先级、资格、配额和提供商级模型配置 |
| Usage billing record | 一次只能应用一次的资金或额度变更 | 用 `request_id + api_key_id` 认领，关联付款用户、行为用户、团队、Key、分组和提供商 |
| Usage Log | 已完成请求的可查询记录 | 保存端点、模型链、token 和媒体用量、金额和归属；用于统计和审计，扣费以资金账本为准 |

分组配置、回退目标、管理和复制用例在 `internal/routing`，SQL 和 Ent 实现在 `routing/postgres`。价格配置管理、价卡读取和价格缓存也在 routing；模型映射、白名单和功能设置由单独的分组策略管理。app 把同一个存储和缓存实例交给 Key、身份管理和 billing。分组值直接使用 `routing.Group`，管理操作进入对应的用例。分组管理直接读取 ProviderStore 和 KeyStore；容量查询使用提供商存储的批量或逐组只读数据，预取失败时回退逐组查询，空结果和每行阈值的读取时机各自保持。

分组和价格配置的增删改查、分组复制和排序的 HTTP 在 `routing/httpapi`，普通用户和管理员的 DTO 在它的 `dto` 子包。分组用量、容量、关联 Key、倍率和 RPM 端点由 HTTP 处理器组合几个小接口完成：倍率配置由 billing 执行，Key 列表由 apikey 提供，用量和 Live 平台检查通过 app 绑定的只读接口读取。

创建或更新分组时，排序锁和提供商关系的复制、替换都在同一个事务里完成。提供商关联由 `provider/postgres` 的同连接参与方法写入，用户授权清理由 `identity/postgres` 参与。调度 outbox 的编码、同连接写入和消费由 `scheduler` 和它的适配层负责；各入口在同一事务里写 outbox，提交后尽力发布。价格配置缓存发布时复制一份独立的副本，返回给调用方的嵌套 JSON 配置也是副本，管理输入或调用方修改副本不会影响其他请求。

分组是客户端选择的产品单位，价格配置是后台共享的价格单位，提供商是调度执行的单位。三者分开建模：同一分组可以聚合不同平台的提供商，不同分组可以有不同的产品策略；多个分组可以共用一张价表，同时保留各自的基础倍率；一个提供商可以加入多个分组，每次请求时单独检查资格。

普通 Key 的 `user_id` 是付款用户。团队 Key 同时带有 `team_id` 和创建者或行为成员的信息，结算命令里的 `UserID` 和 `ActorUserID` 分别表示付款的 owner 和实际调用者。Key 自身还有状态、过期时间、总配额、滚动金额限额、IP 规则和模型重定向。

<a id="api_key_request_limits"></a>
### API Key 请求上限

用户可以在 Key 的创建和编辑表单设置 `concurrency_limit` 和 `rpm_limit`，两项都接受非负整数，0 表示不限制。更新接口省略字段时保持配置，传 0 清除该项限制。个人和团队 Key 使用相同规则，用户、团队和分组的限制继续独立检查。

网关完成认证和资金检查后，在 Redis 中原子预占 Key 的并发槽和 RPM。并发上限统计进入网关后尚未结束的请求，包括等待、流式响应和 Responses WebSocket 中正在处理的轮次。RPM 统计最近 60 秒获准进入网关的请求，上游失败也计数，网关内部重试使用同一次预占。Responses WebSocket 每轮计一次 RPM，轮次完成后释放并发槽，空闲连接由独立的连接数限制管理。同一轮的提供商故障转移继续使用已经预占的额度。其他持续中继的 WebSocket 在连接建立时预占，断开时释放。复合 Key 的所有分组共用这两项计数。

超限返回 429 和 `Retry-After`。并发槽每 30 秒续租，租约有效期为两分钟，请求结束后归还。续租失败通过独立的内部信号取消请求，图片、Anthropic 和 Qoder 流式请求等与客户端断连脱钩的上游也会收到该信号。`pkg/requestcontext` 提供内部终止和断连隔离，隔离后的 context 直接读取已有信号，构造请求后的释放回调为空操作，context 在内部终止时取消。Responses WebSocket 监听内部终止信号，客户端断连后继续读取已经发出的 HTTP 上游结果。实例退出留下的租约在过期后释放。Redis 命令重放按请求 ID 复用预占结果，返回不确定错误时清理该请求的并发槽。配置了请求上限但 Redis 不可用时返回 503。用量查询、模型列表和批任务读取、取消等由网关标记的非消费接口跳过这两项检查。

请求上限随认证快照版本 47 下发，修改后通过认证缓存失效通知传播到各实例。迁移 `288_api_key_request_limits.sql` 为存量 Key 写入默认值，并扩展数据库失效触发器。

### API Key 结算来源

`api_keys.billing_mode` 和可空的 `preferred_subscription_id` 决定资金来源。历史 Key 和迁移后的默认值都是 `auto`。

| 模式 | 运行时选择 | 额度不足或失效时 |
| --- | --- | --- |
| `auto` | 优先使用当前分组可以消费的订阅，然后使用付款主体的余额 | 订阅和余额可以混合分配，订阅不够的部分由余额补足 |
| `subscription` | 请求准入只使用 `preferred_subscription_id` 指向的付款主体订阅 | 订阅不存在、到期、暂停、套餐不覆盖最终分组，或者预检时额度已用完，直接拒绝。已经放行的普通请求，如果最终费用超过了剩余额度，订阅扣到上限，超出部分扣付款主体的余额，余额可以变负；其他订阅不参与 |
| `balance` | 只使用付款主体的余额 | 跳过所有订阅的解析和分配，持有的套餐额度保持不动 |

创建或修改为 `subscription` 时，服务校验订阅属于实际的付款主体并且当前有效。个人 Key 使用本人的订阅；团队 Key 使用 Team Owner 的订阅，成员自己的订阅不能被团队 Key 选择。套餐没有配置分组时，不限制分组；配置了分组时，指定订阅的 Key，其普通分组或复合映射只能取"用户已有权限"和"套餐分组"的交集。分组不可用时的回退、复合 Key 最终选出的分组，以及 handler 的特殊回退，都要再次验证这个交集；配置页面的过滤只是界面提示。

## 路由决策

从客户端模型到上游模型，依次经过：复合 Key 选组、Key 级一跳重定向、分组映射、分组限制和提供商级映射。每一层都保留输入和输出，形成 `requested_model`、`group_mapped_model`、`upstream_model` 和去重后的映射链，供权限判断、计价、日志和响应元数据使用。

请求依次完成：选组、分组权限和客户端协议检查、模型映射、组内提供商资格过滤、调度、按选中的提供商转换并执行、结算。HTTP 路由不按分组平台预先固定处理器。

选定分组后，候选提供商至少要满足：

- 属于这个分组；专用入口声明了强制平台时，平台也要匹配；处于可调度状态并且没有过期。
- 分组策略和提供商都允许当前的模型、端点和认证类型；需要时通过模型映射得到最终的路由键。
- 具备所需的能力或上游资格，例如图片、视频、Realtime、隐私设置、付费媒体或站点能力。
- 没有被本次 failover 排除，不在临时不可调度窗口内，配额和限流状态允许继续尝试。
- 并发槽、等待队列、优先级和负载、会话粘性共同允许本次选择。

普通 Key 需要绑定分组；历史上没有绑定分组的 Key，凭据仍然保留，但新的调用会要求先选分组。系统没有自动默认分组，也没有不经过分组的调度路径。提供商可以暂时不加入任何分组，这时它不参加调度。

分组可以为客户端受限、无效请求和分组不可用三种情况配置回退目标。Key 的 `fallback_when_group_unavailable` 使用管理员配置的不可用回退分组；管理员没有配置目标时，请求结束。每次换组都重新检查用户、团队、复合 Key、订阅范围、模型和协议权限，并检测回退循环。分组回退可以换到另一组平台的提供商，原分组的授权结果要在新分组上重新验证。

提供商白名单缺失或为空时，使用平台和认证类型对应的默认目录，手动配置的映射可以增加自定义的请求名。非空的白名单限定最终的模型范围，支持末尾通配符和单独的 `*`；扩展后的范围仍受原生协议、端点、认证和媒体资格限制。模型名前缀和提供商平台无关，开启协议透传也不代表支持所有模型。

OpenAI 兼容的 Messages 请求，在还没向客户端提交响应时，如果提供商错误命中了管理员配置的临时不可调度规则，会被提升为 failover，即使这个上游状态码通常不触发换号。命中模型范围的提供商先写入模型级的临时排除，再选择下一个提供商。请求内容或 Grok 内容策略导致的拒绝走各自的处理，不进入这条提供商错误路径。

### Fast、推理档位与提供商观测

分组通过 `openai_fast_policy` 选择：跟随请求、强制 Fast、强制 Ultra Fast，或关闭两种加速。全局规则优先级最高；分组级关闭后，Key 无法重新开启；分组级强制开启时，Key 仍可以关闭。详细的优先级和旧布尔字段的兼容见 [Fast 与 Ultra Fast 策略](../interfaces/openai_upstream.md#openai_fast_policy)。

关联的价格配置还可以开启 `free_openai_fast`。最终使用 OpenAI 提供商、计费档位是 `priority` 或 `fast` 时，网关发往上游的仍是 Fast 档位，用户价格用同一分组、价格配置、长上下文和高峰规则按 Standard 重新计算。Usage Log 的 `total_cost`、提供商统计和提供商额度保留 Fast 成本；`actual_cost`、余额和订阅分配、API Key 配额使用 Standard 价格。缺少 Standard 价格时，按现有的缺价零成本记录流程处理，上游请求保持 Fast。其他平台、普通档位和不可信的认证上下文都忽略这个字段。

分组还可以设置 `max_reasoning_effort` 和 `max_reasoning_effort_over_limit`。策略只处理客户端明确传入的 `reasoning.effort`、`reasoning_effort` 或 Messages 的 `output_config.effort`；客户端没传时，桥接器补出的默认值不算客户端请求。先按分组的模型范围映射（精确、前缀或后缀）得到有效档位，再按 `minimal < low < medium < high < xhigh < max` 比较：`downgrade`（默认）改写为上限值，`deny` 返回本地 403 权限错误并标记为业务限制。

推理档位只会被管理员配置的映射或上限策略改写，普通转发层保持客户端的值。`none` 可以出现在映射和请求审计里，但不参与上限排序。Usage Log 同时保存策略前的请求档位和最终转发的档位。复合 Key 在鉴权阶段选出具体分组，之后使用这个分组的策略。HTTP Responses、Chat、Messages 转换，以及 Responses WebSocket 的每个请求帧，都执行同样的判定，策略快照随 API Key 认证缓存传播。

推理映射和上限按分组保存，实际执行时根据选中的提供商、目标协议和模型能力应用。Anthropic 原生档位和 OpenAI 档位的支持范围由各自的执行器校验，混合分组也无法让提供商接受它本来不支持的值。兼容桥区分 `xhigh` 和 `max`，最终的计费档位在转换中保持不变。

网关在 `requeststate.ExecutionHints` 里保存本次规范化后的健康检查模型，`gateway/provider` 把原始模型、规范模型、thinking 和端点固定为提供商的观测输入。调用后回写提供商副本时，只覆盖这个入口负责的字段，因为观测快照只包含部分提供商数据。

用户和分组的 RPM 准入、提供商软计数和三区规则由 scheduler 负责，在资金检查之后执行，故障时按现有规则放行。五小时费用窗口规则、批量查询和回填由 billing 负责，usage 聚合通过只读接口读取；费用和消费字段不在调度的写权限范围内。

## 可用性与缓存

认证、分组、价格配置和提供商的热路径用缓存或调度快照减少数据库压力，数据以数据库配置和实时调度状态为准。以下变更要主动让对应缓存失效或发布新快照：Key 的状态、限额或映射变化；团队关系变化；分组的协议、能力或倍率变化；价格配置的成员或价格变化；分组路由策略变化；提供商的状态、分组关系、凭据、代理、并发或资格变化。

价格配置缓存按分组关联、配置和模型规则查找价格，不读取分组或提供商的平台。模型映射、白名单和协议策略单独保存在分组快照里。价格配置的成员或价卡变化时，价格缓存失效；分组策略和提供商关系变化时，相应的认证缓存、模型目录和调度快照失效。事务提交失败时不发布新规则。

"可认证""可消费"和"可调度"是三种不同的状态：

- Key 可认证：凭据、用户、团队、IP 和资源归属都有效。
- Key 可消费：在可认证的基础上，余额、订阅、Key 配额和滚动限额也允许。
- 分组可路由：产品策略允许这个请求，并且组内有满足模型和协议要求的提供商。
- 提供商可调度：还取决于瞬时并发、上游限流、配额、临时封禁和 endpoint 能力。

模型列表展示的是当前身份理论上可以请求的模型集合。一时没有空闲并发，不代表这个模型永久不可用；实际请求在调度时会重新确认实时状态。

## 价格规则

<a id="group_model_pricing"></a>
### 共享模型价卡与计费设置

价卡和金额算法只在 `billing/pricing` 实现。app 构造 Calculator 和 PriceResolver，通过价格配置接口按分组关联读取有效的价卡和计费设置。分组只保存基础倍率 `rate_multiplier`；模型覆盖价、高峰、长上下文、免费 Fast、批量图片折扣、搜索和语音单价都在价格配置里。

价格的解析顺序是：共享价格配置，然后统一模型目录价格。配置级设置的生效与是否命中模型价卡无关，只有计费设置、没有模型条目的配置也会生效。分组没有关联配置，或者配置已停用、已删除时，使用统一的默认设置和目录定价。价卡支持 token、按次、图片、视频、上下文区间和分时倍率。

手动填写的单价（包括零价）覆盖基础价格。区间里没填的价格桶、区间倍率，以及没有命中任何区间的请求，使用价卡的默认单价；默认单价也没填的桶，继承内置单价。只设置了 Fast/Flex、Max 推理或分时倍率的条目，保留内置的价格桶、来源和计费模式；缺价的模型不会因此得到免费的基础价。上下文区间只有倍率、没有可继承的基础价时，返回 `ErrModelPricingUnavailable`。

价格配置统一保存这些设置：高峰窗口和倍率、`long_context_pricing_enabled`、`free_openai_fast`、批量图片折扣和预扣倍率，以及可空的搜索和语音单价。默认值：内置长上下文开启，高峰和免费 Fast 关闭，批量折扣 0.5，预扣 0.6。可空价格读取目录版本里的 `_billing_defaults`，手动填写的零价表示免费。设置和价卡都通过配置缓存读取并复制，修改返回值不会影响之后的请求。

提供商统计价卡和用户分组倍率由 billing 管理。提供商的 `rate_multiplier` 只影响提供商成本统计和额度累计，用户扣款与它无关。免费 Fast 只让实际使用 OpenAI Fast 档位的用户按 Standard 基础金额分配资金，Usage Log 的 `total_cost` 和提供商成本仍是 Fast 金额。Qoder 和其他平台使用相同的价格回退规则。

`PricingAt` 为零时，价格配置的分时规则不生效；目录声明的分时规则所需的时刻单独计算，配置的分时规则仍然保持关闭。时区由 provider 加载，纯计算只接收传入的 Location。网关在结算开始时读取配置级设置，认证快照里没有分组价格字段。

资金分配始终分别携带订阅倍率和余额倍率；第一个订阅的 `ActualCost / TotalCost` 是订阅侧的倍率，余额的按量倍率另外计算。确定最终计费模式后，只有 token 模式给这两种倍率和套餐倍率叠加高峰因子；图片、视频和按次模式的高峰因子固定为 1。订阅不够时，超出部分按余额侧的倍率结算。

统一结算按价卡声明的计费模式分派，模型名称不影响计费模式。`image` 模式按尺寸查价。`per_request` 先匹配非空标签，再匹配没有声明标签的总输入上下文区间，最后使用明确填写的默认按次价；尺寸标签条目不参加上下文匹配，模型名里有 `image` 也一样。全部没有命中时返回缺价，数值字段的默认值 0 不代表免费。

图片和视频使用价格配置的价卡和目录默认价，分组没有单独的单价或倍率。普通网关里：图片模式乘以实际张数，视频模式乘以输出的总秒数，按次价卡乘以输出数量，token 价卡按实际用量计费。创作台和批量图片按张预占和结算，固定的单张价格来自图片价卡，或者与上下文无关的按次价卡；输入量未知时，按次的上下文区间不能用于固定预占。只有 token 价卡时，查询同一型号在目录里的按张价格，每 token 单价不能直接用作单张价格。已经提交的任务，按提交时的定价和资金快照完成结算。

### 兼容协议的计费候选

Kimi、Zhipu、DeepSeek 的提供商虽然兼容 Anthropic 协议，实际提供的并不是 Claude 模型，所以计费候选不会按客户端传来的 Claude 名称去借用其他型号的价格。只有价格配置为这个候选手动配置了价格时，才保留该候选；经过提供商或分组映射后的实际 CN 模型，按正常优先级解析。候选全部被过滤，或者没有任何非空模型时，返回 `ErrModelPricingUnavailable`，按现有流程记录零成本告警并保留 Usage Log。

### 长上下文

长上下文是模型或价格配置公开的价格策略，和提供商能力无关。价格配置有有效的 token 区间时，按总输入量命中区间，模型内置的长上下文倍率不再叠加；这些区间是管理员配置的价格，不受内置长上下文开关影响。没有有效区间时，由价格配置的 `long_context_pricing_enabled` 决定是否使用模型定价里的阈值和输入、输出倍率；新增的设置默认开启，关闭时只去掉内置阶梯。价格配置的 token 价卡可以直接配置自定义区间。

总输入量包括输入、缓存创建和缓存读取。各模型按自己的阈值规则判断是否进入长上下文档；进入后，整次会话的输入侧和输出侧分别应用对应的倍率。模型目录里的 `input/output_cost_per_token_above_*k_tokens` 在加载时换算成阈值和倍率；条目里手动写了任何一个 `long_context_*` 字段（包括 `0`）时，以这个值为准。本地补充数据可以新增有明确依据的价格和缺失的维度，目录已有的字段保持不变。用户售价在分组关联的价格配置里设置，覆盖文件不参与定价；补充数据里有非法字段或非对象条目时，整次目录更新被拒绝。

模型广场公开的上下文区间价格，和相同分组倍率下的 `ActualCost` 一致。计费模型、服务层级、最终 effort、用量、时刻和倍率都相同时，普通提供商和 Spark 影子提供商得到同样的价格。提供商 `extra` 里已废弃的 OpenAI 开关不参与判断；`long_context_billing_applied` 只在这条规则实际增加了费用时记为真。

### 提供商成本

提供商成本基数优先取 Usage Log 的 `provider_stats_cost`，这个字段为 `nil` 时才用 `total_cost`；填写 `0` 表示提供商成本为零。提供商统计和提供商的 `quota_used` 都用这个基数乘以提供商的 `rate_multiplier`，两者的算法一致。用户余额、订阅和 API Key 配额始终使用 `ActualCost`，不受提供商成本影响。提供商成本回退到模型文件定价时，使用 Usage Log 最终记录的服务层级，并和模型的长上下文倍率一起计算；自定义的提供商统计价格直接作为最终的成本基数，计算时不乘服务层级倍率。提供商统计先匹配独立的提供商成本规则，再尝试网关默认模型价；缺价时按日志层现有的 nil 回退处理。

所有共享价卡和提供商成本价卡使用同一个模型命名空间。同一张价表里，同名模型只有一条规则，所有平台共用；确实不同的模型使用不同的公开模型 ID。不同的提供商成本规则按各自的分组、提供商匹配条件和排序分别保存，互不合并。旧价卡迁移时，可以直接比较的单价逐项取最大；模式、区间、倍率或继承关系无法比较时，需要先处理冲突，见[部署与数据库迁移](../operations/deployment_and_migrations.md)。

共享价格配置只声明计费规则。分组白名单和它的检查阶段见[分组模型与功能策略](gateway_policy_controls.md#group_routing_policy)。

### 计费维度

价格配置的模型定价声明计费模式和计费模型来源：

| 维度 | 可选值 |
| --- | --- |
| 计费模型来源 | 客户端请求模型、分组映射模型或最终上游模型 |
| 计费模式 | token、按次、图片、视频等，由对应的价格字段和区间校验约束 |
| token 桶 | 输入、输出、缓存创建、缓存读取，以及适用的图片输出 token |
| 倍率 | 系统默认、分组、用户覆盖、订阅计划的分组倍率和高峰因子 |

计费来源是上游模型时，要等选定提供商、完成最终映射后，才能确定价格。模型白名单按分组配置的检查阶段执行，计费模型来源变化不影响权限。高峰倍率按请求结算的时刻和配置时区计算，只叠加到适用的 token 价格上；按张计费的图片和按秒计费的视频，使用普通的分组、用户或订阅有效倍率，不叠加 token 专用的高峰因子。所有价格和倍率都拒绝负值，写入配置时校验所选模式需要的字段。

定价模式的冲突检测复用定价缓存键的归一化规则：只忽略大小写和首尾空白，点号、短横线、日期和档位后缀都保留。不同的完整 ID 可以配置独立的价格，前后端校验和缓存键使用同一套规则。

### 分时价格

分组和价格配置的 token 模式模型定价可以配置 `time_pricing`：

- 使用 IANA 时区和每天重复的左闭右开区间，格式为 `HH:mm` 或 `HH:mm:ss`。
- 倍率是有限数，最小 `0.01`，最多两位小数；区间之间不能重叠。
- 结束时间 `00:00` 表示当天 24:00，跨午夜的区间要拆成两段。
- 倍率只作用于 token 的输入、图片输入、输出和缓存价格桶；按次、图片和视频模式不受影响，也不会复制到提供商统计规则。
- 只有倍率的分组条目，没有设置分时规则时继承价格配置的规则；设置后整体替换价格配置的规则（规则时段之外为 1x），所以任何时刻只有一层分时倍率生效。分组的高峰倍率另外叠加。

管理员写入时由后端最终校验。价格配置的分时规则存在 `pricing_config_model_pricing.time_pricing` JSONB 列，分组的存在 `groups.model_pricing` JSONB 条目里，对应的迁移文件是 `249_channel_model_time_pricing.sql`。普通请求按结算时刻计算，OpenAI WebSocket 按对应 turn 开始的时刻计算。配置损坏或无法加载时按 `1x` 处理。

### Max 推理倍率

Token 计费还支持单独的 `max_reasoning_effort_multiplier`，只在最终转发档位是 `max` 时生效。目录、分组和价格配置都可以用有限正数声明（`1` 表示不加价），没有明确的值时，任何型号都不加这项倍率。它作用于全部 token 成本桶，和当前价格、服务层级、区间、分时倍率组合；按次、按次的图片和视频，以及搜索附加费用不乘这项倍率。原始请求是 `max`、被策略降档后，按最终档位结算。提供商统计使用模型文件默认价时，同样按最终档位计算；自定义统计价是独立的最终成本，不叠加用户侧的倍率。

价格配置的这个字段由 `268_channel_max_reasoning_effort_multiplier.sql` 持久化，提供商统计规则不接受这个字段。

### 缓存写入分档

缓存写入可以分成 `cache_write_price`（5 分钟）和 `cache_write_1h_price`（1 小时）两档。1h 列为 NULL 时，两档都用旧的那一列，历史价格配置和提供商统计规则的结算结果不变。这个字段适用于价格配置默认价、token 区间和提供商统计价，填写 0 表示免费；用量里缺少分档数据时，按旧的聚合 token 数计算。对应的迁移是 `261_channel_cache_write_1h_pricing.sql`。

### Grok 媒体、搜索和语音

Grok 的媒体、搜索和 Voice 有各自的计价维度：

- 视频按输出秒数计价。价格配置模型价卡的 `video` 模式按 480p、720p、1080p 分档；没有配置价卡时，读取目录里完整型号和分辨率对应的单价。异步创建时不扣费，第一次观察到任务完成时，用任务级的稳定 request ID 结算。
- 搜索按 `search_price_per_1k` 和调用次数计费，附加在 token 费用之上；独立的 `/web_search` 和 `/x_search` 纯工具请求也可以单独结算。
- Realtime、TTS、STT 分别按每分钟、每百万字符、每小时计价。Realtime 握手和纯文本会话不收费，任一方向观察到非空的音频数据后，才按这个连接的会话时长结算。

<a id="missing_model_pricing"></a>
### 缺价处理

统一文本入口的 Responses、Chat Completions 和 Messages 在选定提供商后、调用上游前检查计费模型的价格。Gemini 的 `generateContent` 和 `streamGenerateContent` 在每次提供商尝试前执行相同检查，覆盖 Gemini 和 Antigravity 提供商。`countTokens` 跳过价格预检。Responses WebSocket 每轮重新检查，包括透传和 HTTP 桥接。查价复用结算的模型来源、共享价格配置和目录价格，Key 重定向、分组映射、提供商映射和换组后的价格各自生效。手动填写的零价和有效的区间价允许调用；缺少基础价的倍率配置按缺价拒绝。尚未开始响应时，HTTP 返回 400，已开始流式响应时追加错误事件。OpenAI 错误码为 `model_pricing_unavailable`。Gemini 返回 Google 格式的 400 `INVALID_ARGUMENT`。WebSocket 按本地策略关闭连接，并提示管理员配置价格或模型映射。

`codex-auto-review` 等目录未收录的内部型号需要手动配置价卡，或者映射到已定价的型号。管理员可以填写零价表示免费。型号在网关的支持列表中，表示可以转发该型号，价格仍需单独解析。

价格预检先按当前请求的协议回退配置解析提供商的上游协议，再选择转换或透传对应的计费模型。经 Responses 执行的 `/responses/compact` 请求复用 `CompactExecutor` 的模型选择：提供商的 `compact_model_mapping` 优先，其次是全局 `gateway.openai_compact_model`，两者都未给出型号时使用常规模型解析结果。最终扣费仍按价格配置指定的模型来源查价。普通 Responses 使用常规模型映射。

转发前的缺价拒绝带有 `ErrModelPricingRejected` 标记。文本尝试循环收到该标记后结束请求，已持有的并发槽由尝试释放回调归还。提供商失败反馈、重试和用量结算在调用上游后的分支处理。

图片型号使用媒体计价流程，文本请求声明图片工具时仍检查文本价格。其他媒体、操作价格，以及请求放行后价格发生变化导致的结算缺价，继续保留已有的缺价记录。操作默认价缺失时报告 `operation pricing unavailable`。发布包只补充了已经核实的 OpenAI Web Search、xAI TTS 和 REST STT 单价。混合搜索计数和通用的 Realtime 时长无法完整表达供应商当前的收费维度，所以没有统一的默认金额，管理员可以自己定价。

所有平台的未知型号都按缺价处理，同系列型号和运行时默认模型的价格都不会被借用。DeepSeek 和其他型号共用目录，费率和峰谷倍率都来自配置。结算只查询配置选定的计费模型；这个模型缺价时，按缺价处理，模型链里的其他型号不参与查价。媒体的独立价卡、手动填写的零价和缺价记录流程各自独立。

<a id="usage_settlement"></a>
## 用量结算

`gateway/completion.Recorder` 负责归一化供应商用量、选择模型和请求 ID、构造 Usage Log；资金预检、查价、分配和提交后的资金处理由 billing 负责。`Eligibility.Check` 只处理资金准入，`gateway/admission.FundingAdmission` 固定它和 scheduler RPM 的顺序：资金检查通过后才累计 RPM；Qoder 等待结束后只复查资金。

用户的日、周、月平台额度已经移除，系统里没有授予、预检、结算累加和后台刷新这项额度的逻辑。余额、订阅、团队、Key 限额和提供商上游额度各自生效。

身份、Key、推广和完成处理共用同一个计费缓存实例。结算通过 `Funds.Settle` 进入 billing/postgres 的一个完整事务；即使 context 里已经有 Ent Tx，结算也不会自动加入外层事务。

billing 根据锁定的订阅快照生成有序的分配和窗口更新，PostgreSQL 适配层负责锁顺序、SQL 更新、outbox 和提交。外层的身份或权益事务通过明确传入的 Ent Tx 复用连接；加入的一方只执行写入，提交、回滚和发布缓存、通知都由外层负责。

使用记录的 `request_id` 表示本地请求，`billing_key` 表示资金操作的去重值。资金命令、账本和去重表中已有的 `request_id` 字段保存计费键。下文的结算去重步骤使用计费键，跨版本规则见[请求 ID 与请求查询](../operations/request_lookup.md#billing_identity)。

标准结算流程：

1. 要求 `request_id` 非空，规范化 `UsageBillingCommand`，根据归属、用量、价格和可选的请求 payload 摘要生成指纹。
2. 在 PostgreSQL 事务里插入 `(request_id, api_key_id)` 去重记录。已有记录且指纹相同，表示请求已经结算过；指纹不同则返回冲突，这次请求不扣费。
3. 先用 `FOR NO KEY UPDATE` 锁定付款用户，再按固定顺序读取并锁定可用的订阅，同一用户的并发消费因此无法超过限额。
4. 按 Key 的结算模式分配资金：`auto` 先分配适用的订阅，再扣余额；`subscription` 只锁定并分配指定的订阅，扣到额度上限，已放行普通请求的超出部分按余额倍率记为欠费；`balance` 跳过订阅，只扣余额。结果分别保存订阅和余额的金额和有效倍率。
5. 在同一事务里累计团队成员的周期用量、API Key 的总配额和滚动窗口。提供商额度按 `COALESCE(provider_stats_cost, total_cost) × provider_rate_multiplier` 累计，成本为零时不累计额度。
6. 提交成功后，返回 `Applied`、新余额、订阅分配，以及提供商和 Key 的配额状态。遇到 PostgreSQL 死锁时，外层开启新事务做有限次数的重试。

API Key 软删除只取消之后请求的准入资格，已经放行的请求照常收费。普通结算按请求快照里原来的 Key ID 累计总配额和滚动用量，允许更新软删除的记录，但凭据、删除标记和状态保持原样；余额、订阅和 Key 用量在同一个幂等事务里提交。Key 确实不存在时，事务失败，结算错误会如实返回。删除和结算并发时，无论谁先提交，费用都会保留；重复提交不会再次扣费。

`users.balance`、API Key 配额和窗口用量的类型是 `NUMERIC(20,8)`。参与这些 SQL 加减法之前，金额先按 PostgreSQL 一致的 half-away-from-zero 规则统一量化到 8 位小数。原因是：如果第 9 位恰好处在 half 边界，余额减法和配额加法的舍入方向相反，会产生 `1e-8` 的对账差额。幂等指纹仍然从量化前的原始金额生成，这样升级前后同一请求的重试不会被误判为冲突；10 位精度的订阅和用量数据保持原精度，命令入口不提前截断到 8 位。

订阅的解析要同时满足生效时间、状态、周期额度和分组覆盖范围。`auto` 模式在没有适用订阅时才使用余额倍率，订阅和余额可以共同承担一笔费用；锁定订阅的模式在请求准入时，只看指定的订阅。普通请求通过预检并成功完成后，如果最终费用超过指定订阅的剩余额度，事务只把能覆盖的部分记到这个订阅上，订阅用量封顶，超出的基础用量按余额倍率从付款主体的余额扣除，余额可以变负。这样后置结算不会因额度不足而失败，也不会留下零计费的记录。这笔余额扣减只用于已放行和并发在途的请求，指定订阅的 Key 不会因此变成按量模式：之后的新请求仍按订阅快照判断，额度用完就拒绝，即使余额充足也一样。

指定的订阅不存在、已失效或不覆盖最终分组时，整笔结算失败，余额不会被当作替代来源。结算命令和幂等指纹都带有结算模式和指定的订阅 ID，异步记录阶段即使 Key 的配置已经变了，也会使用请求时的资金来源。团队请求锁定和扣减的是 owner 对应的付款用户，团队成员的累计用量记在 `ActorUserID` 上，账务归属和行为归属分开。

批量图片和创作台调用 `Funds.Reserve`、`Funds.Capture` 和 `Funds.Release`（只有一个实现）。通用任务引用明确包含 scope、任务 ID 和原来预占动作的 ID。app 注册允许的 scope 和事务参与工厂；`creative/postgres` 和 `batchimage/postgres` 只用 billing 提供的本次 SQL Tx 写自己任务表里的分配和 allowance 标记，billing 不需要知道这两张任务表。未知的 scope 在事务开始前就被拒绝；写任务表失败时，和资金、去重、额度一起回滚；死锁重试时，事务和参与者都重新创建。

scope 和参与信息不加入历史指纹，v1、v2、v3 快照和原来的 request ID 保持兼容。任务使用单独的预占和结算命令：提交时持久化余额和订阅的分配快照，完成或取消时用同一个幂等 request ID 结算、释放差额或回滚相应的预记。指定订阅需要在提交上游之前完整覆盖预占金额，额度不够时回滚并拒绝；普通请求那种"上游完成后把超出部分记为余额欠费"的时序不适用于任务。

## 记录与对账

用户、团队和管理员的使用记录展示单次请求的 TPS：`output_tokens × 1000 ÷ (duration_ms − first_token_ms)`。输出 Token 数使用记录中的 `output_tokens`，耗时字段以毫秒保存。输出 Token 数大于零、首字耗时非负且总耗时大于首字耗时时可以计算；字段缺失或包含非有限数值时显示 `-`。首字耗时为零仍可计算。TPS 在前端通过 `toFixed(1)` 取一位小数，再转换为数值供页面、用户 CSV 和管理员 Excel 共用。页面单位为 `tok/s`，导出无法计算的记录时单元格留空。Excel 保存舍入后的数值，单元格格式补齐一位小数。

网关的完成计算和提交顺序由 `gateway/completion.Recorder` 实现，app 在构造执行器之前，绑定同一个 Forward 和 OpenAI 完成实例。HTTP、SSE、媒体和 WS turn 在提交任务前，取得独立的主体、资金来源、报文和模型快照；后台读取快照，Gin 和之后会变化的请求对象都不再读取。普通完成、Cyber 失败补记和 Live 零费用记录各有自己的资格规则，一种入口的部分失败扣费规则不会套用到其他入口。

完成输入的同步捕获在 `gateway/provider` 里实现：读取 Key、身份和提供商记录，复制实际需要的计费字段，凭据和原始请求体都不保留。请求 ID 前缀的优先级、上游自定义 Header、WS 没有 HTTP 请求 ID 的情况、按 UTF-8 列宽截断、WS turn 的固定时刻，以及明确的额度更新能力，都按既定规则处理。长上下文算法由模型目录和统一定价决定。

普通结算的 `completion.Store` 由 app 直接绑定到 `billing/postgres.SettlementStore`（只有一个实例），和任务的 `Funds` 使用同一个存储。订阅解析由这个存储在调用点读取，普通的 `Apply` 使用自己的完整事务，请求带着外层事务时也不会自动加入。

完成队列停止时，既等排队的任务，也等同步溢出的任务，停止后无法重新扩缩容；完成队列没有持久化。队列或进程超时不代表资金已经提交，资金是否提交以 billing 的幂等记录和事务结果为准，分析记录不能代替。

余额和提供商额度的阈值，由 app 构造的 `billing.BalanceNotifyService`（只有一个实例）判断，完成处理直接使用它。提供商配置通过 `provider/provider.QuotaNotification` 读取：事务返回了状态时，用状态里的用量和限额；没有时再回源读取。邮件的呈现和投递由 notification 负责，通知不参与资金提交。

普通网关在资金事务结束后，尽力写入 Usage Log。日志写入失败不会回滚已经提交的扣费，重试写日志也不会再次扣费。结算失败时，日志保留 token 和基础成本，`ActualCost` 记为零，并返回结算错误，这条记录不算已扣费。资金效果的幂等单位是 `usage_billing_dedup` 和实际的余额、订阅、配额更新；Usage Log 用于分析、展示用户账单和运维排查。

Usage Log 保存付款用户、行为用户或团队、Key、提供商、分组、请求 ID、入口和上游 endpoint、实际执行提供商的平台快照、模型链、计费来源、token 和媒体明细、基础成本、实际成本和 billing type。管理端用量明细可以在列设置里打开默认隐藏的请求 ID 列，直接复制完整的值用于跨日志排查；升级旧的列偏好时，只追加这一列的默认隐藏状态，管理员已有的选择保持不变。增加新协议或新的用量桶时，需要同时更新协议解析、成本计算、结算指纹、日志 schema、聚合查询和对账测试。

管理员使用记录另外保存 `upstream_response_model` 和可空的 `upstream_model_mismatch`。响应模型取自协议转换和客户端别名恢复之前，上游原始声明的模型；比较对象是最终实际出站的模型，比较时忽略首尾空白和大小写，版本、日期和供应商前缀的差异都算不一致。上游没有声明的记录和升级前的历史记录保持 NULL，请求模型不会被拿来补值。这两个字段不参与定价、扣费、模型分布和路由判断。

管理端只在明确不一致时，在模型映射链下方显示橘色箭头和响应模型 ID，悬浮说明列出比较的两个 ID；导出包含原始声明和差异标记。普通用户和团队的用量 DTO 不包含这两个管理员字段。这两列由 `285_usage_upstream_response_model.sql` 迁移创建，单条、批量和降级写入使用相同的字段顺序。

模型明细和模型分布使用不同的展示维度，但可以互相追溯。`requested_model` 保存客户端提交的名称，包括复合 Key 的前缀和 Key 级别名；模型分布的请求维度使用复合选组和 Key 级重定向之后的内部请求模型 `model`。所以用户自定义的名称仍可以在单条记录和映射链里审计，相同的内部模型在分布里只有一项。上游分布和映射分布分别使用实际的上游模型，以及"内部请求模型 -> 上游模型"。

## 领域不变量

- 分组定义产品策略，价格配置定义共享定价，提供商定义执行能力；三者的 ID 互不通用。
- 客户端模型、分组映射模型和上游模型分别保存，限制、计费和响应恢复各自使用明确的来源。
- 缓存只加速判断；已禁用的用户、团队、Key、分组或提供商，命中缓存也无法继续工作。
- 资金、订阅、团队成员、Key 和提供商额度的变化，都在同一个幂等事务里完成。
- 公开的长上下文区间价格，等于用户实际扣费的单价；在同一套计费规则下，提供商平台和提供商 extra 不改变用户价格；价格配置的区间不和模型内置倍率重复叠加。
- 提供商统计和提供商额度使用同一个成本基数和提供商倍率；用户资金和 API Key 配额只使用 `ActualCost`。
- 指定订阅的 Key，最终路由分组要被套餐覆盖；预检发现订阅失效或额度已用完时，直接拒绝，不退回其他来源。已放行且成功的普通请求，由订阅承担到上限，超出部分记为余额欠费，订阅用量不超扣，结算金额也不会是零。
- `request_id + api_key_id` 相同但指纹不同时，按冲突处理。
- Usage Log 不代表扣费事务已提交；对账以去重记录和提供商、权益的实际变化为准。
- 新增计费类型时，测试要覆盖订阅和余额混合分配、团队归属、重复提交、死锁重试和日志写入失败。
