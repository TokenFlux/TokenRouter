# 内容审核与风险处置

本文说明 moderation 模块的审核范围、规则优先级、同步和异步决策、风险处置和数据保存规则。HTTP、PostgreSQL、Redis、外部审核服务和媒体获取，各自通过适配层接入。上游供应商自己的内容政策不在本文范围内；完整的用户内容也不写进普通日志。

- [失败处理](#失败处理)：修改队列、超时或部分失败的处理时读取。

## 作用域与模式

审核模式有 `off`、`observe` 和 `pre_block` 三种。规则可以覆盖全部分组或指定的分组，按 sample rate 抽样，并用 include 和 exclude 模式限定模型。目前的协议提取器覆盖 Anthropic Messages、OpenAI Responses、Chat Completions、Gemini 和图片请求；每种协议只提取当前一轮的用户文本、工具结果和允许的图片输入，历史消息不会被重复审核。

审核发生在调用上游和结算之前。身份归属和计费归属分开处理：团队 Key 的场景下，风险主体是实际行为的用户，付款的 owner 和风险处置无关。监控探测和明确标记的内部请求，可以按策略跳过审核，跳过的原因可以诊断。

<a id="content_moderation_decision_pipeline"></a>
## 决策流水线

1. 按全局模式、分组、模型、协议和抽样率，判断是否进入审核。
2. 从当前请求里提取有长度上限的文本、工具输出和媒体单元，计算预审核 hash。
3. 先匹配阻断 hash、关键词和缓存；再按 `keyword_only`、`keyword_and_api` 或 `api_only` 决定是否调用外部审核。
4. 从健康的 API Key 池里按优先级选出审核凭据，在有上限的并发、超时和重试内执行。
5. 按各类别的阈值生成 allow、block、hash_block、keyword_block 或 error 结果，并记录审核结果。
6. `pre_block` 模式在调用上游之前返回安全错误；`observe` 模式不阻断主请求，异步写入观测和风险结果。

多个审核单元里，任何一个明确命中阻断，请求就被拒绝；其他单元审核失败时，已经确认的阻断照样生效。没有明确的阻断、但审核链路不完整时，按当前模式记录为 incomplete 或 error，这种结果不代表"已审核且安全"。

## 规则与缓存

关键词、阻断 hash、类别阈值、模型过滤、分组范围、审核用的 API Key 和出站代理，都是运行时配置。每个 API Key 带有优先级、元数据、健康状态和冻结时间；连续失败时可以暂时冻结，之后健康检查通过或到了恢复时间，再放回候选。代理引用管理端的 Proxy 记录，解析结果短时间缓存，保存配置时立即让本进程的缓存失效。代理解析或客户端构建失败时，请求按失败处理；改走直连会暴露部署的实际出口地址。

预审核 hash 和规则用缓存降低热路径的开销。保存配置时更新数据库和进程内快照，读取时按 TTL 回源。阻断 hash 存在 Redis 集合里。配置刷新失败时保留旧快照并退避重试；缓存故障时按设计回源或失败，结果不会被当成"已确认安全"。规则列表的顺序和匹配模式影响结果，所以执行时按列表顺序遍历，map 的遍历顺序不可依赖。

## 风险处置

审核日志会累计每个用户的命中次数，在配置的窗口内达到阈值时自动封禁；解封需要管理员手动操作。Cyber warning 有自己独立的警告计数和阈值，可以记录、查询和处置，它和内容审核的 block 结果是两种不同的状态。开启风险控制后，管理员可以从侧栏进入风险控制页面；提示词审计由它自己的功能开关控制。

风险处置要带上实际的用户、API Key、分组、模型、request ID、命中的类别和来源规则。自动封禁失败时发出告警：数据库更新失败意味着后续请求并没有被阻断。管理员可以查看汇总、日志、媒体、warning，测试 API Key，执行解封；所有敏感读取都需要管理员认证，并记录审计。

<a id="moderation_transactions"></a>
### 处置与事务

普通命中按顺序执行状态命令、通知和尽力而为的记录，这几步不在同一个事务里。Cyber warning 使用 moderation/postgres 的完整事务：先锁住用户，再插入 warning 和媒体、更新计数、禁用用户；identity/postgres 在同一个 SQL Tx 里参与用户锁和状态写入，提交和失效通知由外层负责。Cyber 的认证失效和通知在提交后执行，它们失败时，已经提交的处置不回滚。普通命中和 Cyber 各有自己的计数、窗口和管理员处理方式。

<a id="upstream_cyber_policy"></a>
### 上游 Cyber Policy

OpenAI WebSocket 的 `error` 和 `response.failed` 事件都可能带有明确的 `cyber_policy` 错误码。服务层先解析事件的用量并保存风控证据，再进入可能重试、故障转移或提前返回的错误分支；`rate_limit_error` 和 `cyber_policy` 同时出现时，证据同样会被记录。

WS handler 的 `AfterTurn` 根据这个标记执行风控、用量记录和会话阻断；处理完后按轮清除标记，下一轮不会复用这次的命中。事件响应体按现有的长度截断，软警告和硬阻断各有处置规则。

会话阻断的键、转录前缀算法、scope 门禁和存储编排，都由 `gateway/session.CyberBlocks` 负责；HTTP 只在功能和存储都可用时，才按需解析手动指定的会话标识。查找时先检查手动指定的键，再在来源 scope 内做转录匹配；scope 生效后，候选数超过上限时仍然返回阻断标识，截断后的候选集合不能作为放行的依据。Redis 故障时放行（fail-open），旧的单键缓存也能读取。app 直接构造一个 CyberHandler，复用审核运行设置、后台任务跟踪、完成器和 Ops 队列，没有单独的后台池和请求重试。

## 记录与数据保护

审核记录可能包含命中的文本或媒体引用，命中和未命中的记录有不同的留存策略。普通的 Ops 和 system log 只记录必要的元数据、摘要和错误；完整的 prompt、图片、审核密钥和上游原始响应都不写入。管理端展示和删除 hash 或媒体时，检查管理员的授权范围。

`moderation.CheckInput.NoMediaRetention` 为 true 时，进入"无媒体留存"模式（创作台等敏感场景强制开启）：不对命中的媒体做快照，不保存 `input_excerpt` 和正文输入项，审核日志只记录输入 hash、类别、分数和决策等元数据；请求报文里的 base64 媒体和 prompt 明文都不落库。创作台送审时开启这个字段，见[创作台](creative_studio.md)。

返回给客户端的安全消息只说明请求被本地策略拒绝，关键词表、hash、阈值、供应商凭据和可以用来绕过规则的细节都不出现在消息里。上游自己的内容政策错误由平台的错误分类处理，和本地审核命中分开记录。

异步审核和延迟清理由 app 启动。关闭时先停止入队，再等待现有任务和清理循环结束；因配置读取失败而剩下的任务，按未完成的数量报告，不计为已排空。网关正常请求的审核模式、并发、重试和取消策略，在关闭过程中保持不变。

## 失败处理

Observe 模式下，异步队列满、worker 缺失或持久化失败，都不会阻断已经允许的主请求，但会累计 dropped 和 error 健康信号。Pre-block 模式的外部审核有总超时和重试上限，上下文取消时立即停止。代理不可用算作外部审核错误，按当前模式的 fail-open 规则记录，请求不会绕过代理改走直连。更新审核配置、API Key 池或规则缓存失败时，管理端的响应如实报告应用失败。

测试至少覆盖：off、observe 和 pre-block 三种模式；关键词、hash 和 API 的组合；include 和 exclude；部分单元失败时仍然阻断；团队行为用户的归属；缓存失效；按 TTL 回源；日志脱敏；无媒体留存（不快照命中的媒体、不保存正文摘录，但仍记录输入 hash）。
