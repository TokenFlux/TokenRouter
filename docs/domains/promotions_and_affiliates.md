# 推广与返利

本文描述邀请码关系、订单返利、冻结/解冻、余额转入和注册优惠码的不变量。它不定义支付渠道回调字段、营销页面文案或管理员操作教程。

## 邀请关系

每个用户有一个推广档案和唯一邀请码。邀请码统一修剪并转大写，只允许大写字母、数字、下划线和短横线，长度为 4 到 32。管理员可设置自定义码或恢复系统生成码。

用户只能绑定一次邀请人，不能邀请自己。注册阶段在推广总开关关闭时静默忽略邀请码，避免阻断注册；启用后，格式错误、未知邀请码或自邀请返回明确业务错误。用户已有邀请人时幂等保留既有关系；并发首次绑定只有一个关系生效，未获胜的写入返回已绑定错误。绑定以用户 ID 持久化，后续邀请码改名不改变既有邀请关系。

## 返利生命周期

支付订单完成后，以被邀请人实际获得的推理积分为基数计算返利。邀请人的专属比例优先于全局比例；结果按统一精度舍入。返利还受邀请关系、总开关、邀请后的有效天数和每个被邀请人累计上限约束。

返利计提先在 PostgreSQL 事务中锁定邀请人推广档案，再读取该被邀请人已累计的返利并计算剩余额度，计算与写入使用同一事务；有外层支付事务时复用原连接。并发计提不能按同一个旧累计值分别占满上限。

返利写入关联邀请人、被邀请人、金额、冻结时长和可选来源订单。冻结时长为正时先增加 frozen quota；否则直接增加 available quota。历史累计值同时更新，用于统计而不是可重复转账的余额。

已到期冻结记录在读取推广详情或执行相关资金操作时解冻到可用返利；解冻是持久化资金状态转换，不能只在响应 DTO 中相加。管理端统计要区分可用、冻结和历史累计。

## 转入余额

用户只能把当前可用返利一次性转入主余额。promotion 的 PostgreSQL Adapter 在事务中锁定/更新推广档案，通过 billing 的参与能力增加用户余额及累计充值，并写转账记录；没有可用返利返回业务错误。成功后失效余额、认证和推广相关缓存，避免网关继续使用旧余额。

转入不是外部提现，也不调用支付渠道。余额变化之后仍遵守正常计费、退款和审计规则；不能通过删除推广记录撤销已经转入的余额。

## 注册优惠码

Promo Code 在注册成功后赠送余额，具有 code、bonus amount、active/disabled、过期时间、最大使用次数和实际使用次数。`max_uses=0` 表示总次数不限制；每个用户对同一 code 最多使用一次。

应用优惠码在同一数据库事务中对 code 加行锁，重新检查状态/过期/总次数，确认用户未使用，通过 billing 的明确参与能力增加余额，写 usage 记录并增加 used count。正数 Promo 赠送仍沿用旧 `UpdateBalance` 同时增加累计充值的行为；不在迁移中改用普通仅加余额入口。事务提交后再失效余额和认证缓存。预校验只能改善用户体验，不能替代事务内复核。

优惠码与邀请码可以同时出现在注册流程，但语义独立：前者直接给注册用户余额，后者建立未来订单返利关系。Redeem Code、订阅和支付促销不应复用 Promo Code 的表或次数语义。

## 幂等与审计

订单返利以 `source_order_id` 关联来源，repository 对重复来源只应用一次；支付 webhook 重放不能重复计提。Promo Code 依靠唯一 usage 和行锁防止并发重复赠送。邀请码绑定、比例调整、解冻、转账和管理员改码都应保留操作记录或可审计状态。

补偿时先判断订单履约、返利记录和余额流水各自是否已经落地，不得通过再次调用普通成功路径“试试看”。资金相关缓存失效失败要告警，但数据库事务事实仍是权威。
