# 网关错误响应策略

本文描述上游错误分类完成之后，管理员可以配置的客户端错误透传和改写规则。提供商是否重试、是否故障转移，由分类阶段决定；这些规则只影响最终返回给客户端的错误，凭据不会因此透出，失败的请求也不会变成成功。

## 处理位置

平台处理器先把网络、凭据、限流、内容政策、模型或 endpoint、5xx 等错误分类，并决定在同一提供商重试、换提供商还是终止。到了最终的客户端错误阶段，才用本文的规则决定响应的内容。所以：

- 规则不会增加 attempt，也不影响提供商的临时不可调度和 token 刷新决策。
- 规则不改变用量结算的成功或失败，HTTP 错误也不会变成业务成功。
- 流已经开始时，按协议生成 SSE 或 WebSocket 的错误事件；已经发出的状态行无法再改。

失败的事实和稳定的 reason 在 `gateway/forward`，HTTP 层使用 `gateway/httpapi` 的展示数据和输出顺序（只有一份实现）。空的 Chat 终态和空的 Responses completed 各有自己的 Ops 消息，对外仍使用内部静默拒绝的编码；是否换号、怎么完成，由请求编排判断。观察输入只带提供商的 ID、名称和平台，凭据不会交给错误输出层。

OpenAI 的同步错误、SSE 终止帧和写失败时的备用输出，由 `gateway/httpapi.OpenAIErrorOutput` 处理。图片专用错误输出使用同一套响应承诺和流失败观测。接管 Writer 之前，先停止 compact 和图片的心跳，并区分四种情况：只有保活、已经完成的 JSON、实际的 SSE 输出、已经提交的专用错误。普通的流错误和计入 SLA 的失败，分别按各自的规则观测。

图片请求首次 SSE 心跳写出前，上游 451 等错误仍保留原有 HTTP 状态和 JSON 错误对象。并发排队、响应头等待或响应读取阶段的首次心跳提交 HTTP 200 后，图片错误改为一个 `event: error`，保留 `type`、`message` 和已有的 `code`、`param`，诊断记录保留实际失败状态。仅有心跳不算实际图片输出，最终网络错误和重试耗尽也按已经建立的 SSE 格式结束响应。非流式图片的 JSON 空白心跳仍以原有 JSON 错误对象结束。

流式图片上游返回普通 JSON 时，只有完整、有效的 `data[]` 会转换为图片完成事件。HTTP 200 中的 `error` 对象仍是失败，先于 `data` 检查；无效结构、读体失败和正文超限也进入终止错误流程。验证失败不输出成功图片事件，转换过程不会为同一结果再次发起生成或结算。

### 提供商健康分类

提供商健康分类发生在这些展示规则之前，管理员的透传规则改变不了它的结果。

- OpenAI、Kimi、Zhipu、DeepSeek 收到 HTML 格式的 403 时，视为 CDN、代理或端点级的拦截，不增加提供商的 403 计数，也不写临时或永久处罚。结构化的 403 进入累计策略：达到阈值之前临时冷却，达到阈值后才把提供商标记为错误。之后有请求成功并记录用量时，清零这个提供商的计数，所以阈值只反映连续的失败。
- Kimi 返回这条精确文案时：`You've reached your concurrent request limit. Please wait for your ongoing requests to finish and try again.`，属于提供商级的并发限制。请求照常返回可故障转移的信号，提供商只被标记为临时不可调度，默认 10 分钟，不计入累计的 403 永久禁用计数；其他相似的文案按普通的结构化 403 处理。
- 其他平台按各自的 403 分类规则处理。

## 规则匹配

启用的规则按 `priority` 从小到大匹配，第一个命中的规则生效。匹配方式：

- `platforms` 是单独的前置过滤：为空表示所有平台，否则请求的平台要在列表里。它不参与 `match_mode`。
- `error_codes` 可以配置多个上游或解析后的错误码，同一维度内任意一个匹配即可。
- `keywords` 在有长度上限的错误正文里做不区分大小写的匹配，同一维度内任意一个匹配即可。
- `match_mode` 只组合已经配置的 `error_codes` 和 `keywords`：`any` 表示任一维度命中，`all` 表示两个已配置的维度都要命中；只配置了一种时，直接使用那一种。

服务只读取错误正文的前 8 KiB 用于匹配，大响应不会放大内存和匹配开销。规则的优先级是明确的业务顺序，以 `priority` 字段为准，数据库的默认顺序和前端列表的顺序都不可依赖。

## 响应与监控

网关内置错误固定使用英文。请求的 `Accept-Language` 和账户语言用于网站展示。错误规则、审核和 Beta/Fast 策略的自定义提示使用单文本配置，管理员填写英文内容。上游透传消息按供应商原文返回。

命中的规则可以保留上游的状态码，也可以使用 `response_code`；消息可以用解析出的上游错误消息，也可以用 `custom_message`。`passthrough_body` 返回的是平台错误提取器得到的消息，并不是完整的原始 body；响应仍按当前客户端协议的格式封装。

`skip_monitoring` 在最终错误或中间的上游错误事件命中时，把当前请求标记为跳过通常的 Ops 错误记录，用于管理员确认过的预期业务错误。access 和 usage 记录、审计、内容审核和其他安全记录照常写入，提供商状态的分类也照常执行。这个开关要谨慎使用，否则同一个请求里的真实故障可能从告警里长期消失。

## 缓存一致性

规则只在 `gateway/errorpolicy` 实现，PostgreSQL、Redis 和管理 HTTP 分别由 gateway 的适配层提供。app 持有一个实例，各执行适配共用它。

服务启动时从数据库加载有序的规则，并维护进程缓存和 Redis 缓存。创建、更新、删除或排序之后，写入路径更新缓存，并通过 Redis 发布失效通知，订阅回调重新加载规则。规则以数据库为准；缓存或通知失败时，保留可诊断的错误，靠后续的重新加载恢复一致。

本进程内的管理写入、回源和缓存发布使用同一个可取消的协调器，所以新的写入发布之后，旧的读取无法把旧规则写回来；缓存的输入和匹配结果都是独立的副本。停止时，先取消启动时的预热和订阅回源，再在应用剩余的预算内等待；超时时报告清理未完成。这个协调只在单个进程内有效，Redis 协议没有变化。

规则更新原子地写入 enabled、priority、匹配条件和响应动作，不会短暂发布只更新了一半字段的规则。管理端的测试或预览使用同一个匹配器，前端不重新实现规则逻辑。

## 安全要求

上游的 message 可能包含 URL、内部 ID、请求片段或供应商的调试信息。启用透传之前，要确认平台的提取器已经去掉 token、Authorization、Cookie、代理凭据、service account、内部 project 和完整的用户内容。无法确认时，使用 `custom_message`。

测试覆盖：规则优先级、any 和 all、空平台、大小写、8 KiB 上限、非流式、流式和 WebSocket、Redis 失效通知、`skip_monitoring`，以及没有命中时的默认错误。实现有变化时，还要验证 failover 和结算的行为保持不变。
