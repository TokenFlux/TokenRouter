# 网关错误响应策略

本文描述上游错误分类完成后，管理员可配置的客户端错误透传与改写规则。它不定义账号是否重试、是否故障转移，也不允许泄露凭据或把失败请求改成成功。

OpenAI 的同步错误、SSE 终止帧与写失败兜底由 `gateway/httpapi.OpenAIErrorOutput` 唯一实现。文本入口沿用自身的观测端口，WS、图片及其他执行适配直接使用同一默认输出器。接管 Writer 前仍先停止 compact 和图片心跳，并区分仅保活、已完成 JSON、真实 SSE 输出以及已提交的专用错误；普通流错误和计入 SLA 的失败分别保留原观测口径。

## 处理位置

平台处理器先把网络、凭据、限流、内容政策、模型/endpoint 和 5xx 错误分类，并决定同账号重试、换账号或终止。只有到达最终客户端错误阶段，才使用本专题的规则选择响应形状。因此：

- 规则不增加 attempt，不改变账号临时不可调度或 token refresh 决策。
- 规则不修改用量结算的成功/失败，也不把 HTTP 错误转为业务成功。
- 流已开始时仍要生成对应 SSE/WebSocket 错误事件，不能改写已经发送的状态行。

失败事实和稳定 reason 位于 gateway/forward，HTTP 使用 gateway/httpapi 的唯一展示投影及输出顺序。空 Chat 终态和空 Responses completed 保留各自的 Ops 消息，但继续使用原内部静默拒绝编码；换号资格和完成处理仍由请求编排判断。观察输入只携带账号 ID、名称和平台，不把凭据交给错误输出层。

账号健康分类发生在这些展示规则之前。OpenAI、Kimi、Zhipu、DeepSeek 收到 HTML 外形的 403 时，视为 CDN、代理或端点级阻断证据，不递增账号 403 计数，也不写临时/永久处罚；结构化 403 则进入同一累计策略，阈值前临时冷却，达到阈值后才标记账号错误。后续成功且进入用量记录的请求会清零该账号计数，保证阈值只表达连续失败。其它平台继续使用各自既有 403 分类，管理员透传规则不能改变这些状态决定。

Kimi 返回精确文案 `You've reached your concurrent request limit. Please wait for your ongoing requests to finish and try again.` 时属于账号级并发限制：请求仍返回可故障转移信号，但账号只写入默认 10 分钟临时不可调度，不进入累计 403 永久禁用计数；其它相似文案仍按普通结构化 403 处理。

## 规则匹配

启用规则按 `priority` 从小到大匹配，首个命中规则生效。匹配顺序为：

- `platforms` 先做独立前置过滤：为空表示全部平台，否则请求平台必须属于配置列表；它不参与 `match_mode`。
- `error_codes` 可配置多个上游/解析后的错误码，同一维度内为 OR。
- `keywords` 在受限长度的错误正文中做不区分大小写匹配，同一维度内为 OR。
- `match_mode` 只组合已配置的 `error_codes` 与 `keywords`：`any` 表示任一维度命中，`all` 表示两个已配置维度都命中；只配置一种时直接使用该维度。

服务只读取错误正文前 8 KiB 用于匹配，避免大响应放大内存和规则成本。规则优先级是显式业务顺序；不能依赖数据库默认顺序或前端列表顺序。

## 响应与监控

命中规则可以选择保留上游状态码或使用 `response_code`，并选择解析后的上游错误消息或 `custom_message`。`passthrough_body` 不是返回完整原始 body，而是使用平台错误提取器得到的消息；响应仍由当前客户端协议封装。

`skip_monitoring` 在最终错误或中间上游错误事件命中时，为当前请求标记跳过通常的 Ops 错误记录，用于管理员确认的预期业务错误。它不能跳过 access/usage、审计、内容审核或其它安全记录，也不能阻止账号状态分类。应谨慎使用，避免把同一请求中的真实故障从告警面永久隐藏。

## 缓存一致性

规则唯一实现位于 `gateway/errorpolicy`，PostgreSQL/Redis 与管理 HTTP 分别由 gateway Adapter 提供。app 直接持有唯一实例，执行适配共享该实例。

服务启动时从数据库加载有序规则，并维护进程缓存和 Redis 缓存。创建、更新、删除或排序后，写路径更新缓存并发布跨实例失效通知；订阅实例重新加载。数据库仍是权威来源，缓存/通知失败必须保留可诊断错误并允许后续重载收敛。

本进程的管理写入、回源和缓存发布使用同一可取消协调器，旧读取不能在新写入发布后恢复旧规则；缓存输入与匹配结果提供独立副本。停止先取消启动预热及订阅回源，再按应用剩余预算等待，不把超时等同于已完成清理。这不增加跨进程写入协调或新的 Redis 协议。

规则更新需要原子地保持 enabled、priority、match 条件和响应动作，不能短暂发布只含一半字段的规则。管理端测试或预览应复用同一匹配器，避免前端重写规则语义。

## 安全边界

上游 message 可能含 URL、内部 ID、请求片段或供应商调试信息。启用透传前必须确认平台提取器已移除 token、Authorization、Cookie、代理凭据、service account、内部 project 和完整用户内容。无法证明安全时使用 `custom_message`。

测试应覆盖规则优先级、any/all、空平台、大小写、8 KiB 上限、非流/流/WebSocket、跨实例失效、`skip_monitoring` 和未命中默认错误。相关实现变化还要验证不会改变 failover 和结算。
