# 请求 ID 与请求查询

本文记录请求 ID、诊断记录、计费关联和请求详情查询。用量聚合见[使用记录与运维预聚合](pre_aggregation.md)，升级步骤见[版本升级说明](upgrade_notes.md#request_id_unification)。

<a id="request_identity"></a>
## 请求标识

全局 HTTP 入口生成本地 UUID，网关中间件复用它。`X-Request-ID`、`X-TokenRouter-Request-ID` 和兼容的 `X-Sub2API-Request-ID` 返回同一个值。响应 writer 在提交正文、刷新和连接升级前恢复这些头，上游响应头因此无法替换本地请求 ID。浏览器可以通过 CORS 读取这些响应头。

调用方的 `X-Request-ID` 和 `X-Client-Request-ID` 保存为调用方别名。合法的 `X-Client-Request-ID` 继续回显，缺失时使用本地 ID。别名用于查询，权限根据认证主体、记录归属和团队关系判断。

提供商重试和切换共用入口 ID。WebSocket 在每轮开始时生成请求 ID，提供商切换和重试复用该轮 ID，并保存连接请求的 ID。异步任务使用从稳定业务键派生的统一格式 ID，重放得到同一个值。上游请求 ID 和响应 ID 保存为不同类别的外部别名。

<a id="request_identifier_sources"></a>
## 请求查询中的标识来源

请求查询按来源展示调用方请求 ID、上游请求 ID和响应 ID。调用方标识来自客户端传入的请求头；响应 ID来自协议解析结果，例如 Responses 响应对象的 `response.id`。历史 `upstream` 别名缺少分类证据时，显示为类型未记录，不根据值的前缀推断。

每次上游派发固定提供商、尝试编号和响应头名。提供商未配置 `upstream_request_id_header` 时，请求查询读取上游响应的 `X-Request-ID`；配置后只读取指定头。指定头缺失或为空时不记录，也不回退读取其他头。配置为 `X-Client-Request-ID` 时，只记录上游实际返回的值，其来源不代表该值一定由上游生成。

请求摘要的别名 JSON 保存实际来源、提供商和尝试编号，现有别名索引继续按值查询。响应头在到达时记录，已解析到的 Responses 流响应 ID在流中断前即可保留。后续空观测不能清除同次尝试的标识，延迟响应通过固定的派发引用更新所属尝试。不同尝试可以保留不同 ID，界面分别标明归属。媒体完成结果携带实际派发引用，因此选中响应头缺失或重复时仍能更新正确的尝试。没有上游响应的提供商认证失败保留为未编号记录，与已派发的尝试分别展示。

图片和视频结果经过媒体循环的双向转换时，保留原派发引用。HTTP 拒绝在收到响应头时标记对应尝试失败，协议错误回调使用响应所属的派发引用补充状态和原因。没有响应的网络失败或取消由传输层更新所属尝试；请求整体的取消状态由入口记录。上述采集也适用于没有文本性能计时器的媒体请求。

WS 转 HTTP 使用传输层的派发编号，响应头、响应 ID和性能记录归属同一次尝试。图片 URL 转 Base64 的 CDN 下载属于交付过程，不新增模型尝试。视频等关联请求已采集标识时，用量写入利用现有父子关联避免再次加入未分类或截断的上游 ID。

媒体执行器在收到响应后保存派发引用，正文读取和解析结束时记录该尝试的终态；即使出错后不生成用量记录，也保留已采集的 ID。视频内容请求分别记录状态查询和内容下载，前一次处理完成后才开始后一次。WS 的 HTTP 内部重试按每次派发重新计时，最终性能不包含前次被拒绝请求的等待，整轮时长仍从原始开始时间计算。

实际发往上游的 token 计数请求在读取、校验和输出结束时记录尝试终态，不依赖用量写入。计数响应读取或校验失败时，已采集的标识继续保留。本地估算和未派发的“不支持”响应不新增上游尝试；上游拒绝后改用本地估算时，上游尝试仍保留失败状态。

使用记录的 `usage_logs.upstream_request_id` 与请求查询使用相同的响应头选择规则：未配置时读取 `X-Request-ID`，配置后只读取指定头。选中的头缺失或为空时不记录。使用记录将值修剪后按 128 字节截断，并移除不完整的 UTF-8 尾部；WS 轮次的该字段为空。配置和默认值用于之后的请求采集，历史记录保留原值。

<a id="request_storage"></a>
## 记录与写入

`requestlog` 保存到达正常运行服务的请求摘要，包括成功、拒绝、失败、取消和未完成请求。健康检查和 404 也经过记录入口。请求到达应用中间件之前的网络失败没有应用请求记录。

`request_records` 保存起止时间、状态、路径、认证后的归属、模型、失败阶段诊断、上游尝试和关联标识。完整提示词与报文按各业务既有的留存规则处理。未知凭据的请求保留管理员可查的摘要。已匹配 Key 的请求记录 Key 的行为用户和团队归属，认证权限由认证中间件判断。

HTTP 请求和 WebSocket 轮次的起止时间、总耗时和终态由各自入口记录。客户端断开时保留已观测的结束时刻，后台继续读取 usage 不延长这个生命周期。使用记录所属尝试的性能保存在 `usage_logs.timings`，详情利用现有批量关联查询读取，按 usage 行和尝试编号分别展示；不复制到请求摘要，不通过系统日志恢复历史值。

尝试在派发上游请求时编号。失败后切换提供商保留原请求 ID、失败尝试及必要的连接阶段诊断，最终 usage 的指标只属于对应尝试。没有 usage 的鉴权、准入和连接失败继续仅保存请求诊断，阶段计时写入 `failure_timings` 及失败尝试的同名字段。历史 `record.timings` 不再读取。`usage_write_state` 区分待写入、确认写入、确认未写入、跳过和结果未知；写入操作本身的错误、时间及耗时属于诊断，不是上游性能。确认写入也不改变已经记录的请求失败或取消状态。队列拒绝和后台写入异常保留必要阶段诊断，不备份内容首尾或整份性能快照；等待超时之后实际出现的 usage 通过普通关联查询展示，之前的超时事实继续可见。

请求快照使用有上限的内存缓冲，同一 ID 的更新按版本合并。后台每 20 毫秒写入最多 256 条快照，缓冲最多保留 4096 个请求。缓冲已满时，新请求在调用侧同步写库。路径、模型等诊断文本在入队前清除空字符，并按 UTF-8 截断到字段上限。

批写失败时，在同一写入超时窗口内逐条重试。JSON 编码失败或 PostgreSQL 数据异常（SQLSTATE 22）表示该版本的内容无法存储，逐条确认后移出缓冲，并写日志、累计故障次数。其余写入错误保留待写快照，后台批写间隔延长到一秒，写入成功后恢复正常间隔。数据库写入成功或确认内容无效时移除对应版本，写库期间到达的新版本继续等待下一批。

每次写入的超时上限为五秒。正常关闭时等待已开始的同步写入并排空缓冲，关闭超时或写库失败会返回错误。服务停止后收到的快照在调用侧同步写入。进程异常退出会丢失尚未入库的快照，数据库持续不可用时，同步写入也可能失败。失败会写日志并累计故障次数。管理员通过 `/api/v1/admin/requests/health` 查看待写数量和累计故障次数。数据库暂不可用时，管理员按本地请求 ID 查询可以返回本机的待写摘要。

`running` 表示尚未记录终态，可能仍在执行，也可能在进程退出时中断。请求详情对仍存在的创作台和批量图片任务读取任务表的状态。历史记录缺少元数据时使用 `legacy` 标记，各类原始记录分别展示；单独的用量记录不能证明 HTTP 请求成功。

Grok 视频轮询按上游状态更新任务摘要：`done` 对应完成，`failed` 和 `expired` 对应失败，取消状态对应 `canceled`。终态记录结束时间。状态更新在计费认领之前执行，已记过费的视频再次查询时也能显示完成。

## 配置与留存

```yaml
request_log:
  retention_days: 30
```

`retention_days` 默认 30 天，值为 0 时使用默认值。在配置文件的 `request_log.retention_days` 中设置。修改配置后重启服务。

请求摘要有独立的清理任务，Ops 开关和采样配置控制各自的监控数据。用量、审计和计费数据按各自规则留存，摘要过期后仍可查询尚存的业务记录。备份的 Ops 日志选项同时控制 `request_records`。

<a id="billing_identity"></a>
## 计费兼容

新使用记录的 `request_id` 保存统一请求 ID，`billing_key` 保存资金操作的去重值。资金账本和去重表里的既有 `request_id` 字段继续表示计费键。普通请求、WS 轮次和任务使用各自既有的结算规则，外部别名不会替代计费键。

使用记录按 `(COALESCE(billing_key, request_id), api_key_id)` 去重。历史行的 `billing_key` 为空时使用原请求 ID，因此任务跨版本重放共用同一条用量记录。预占、扣款、释放的动作键分别处理资金操作。

`client:`、`local:` 和 `generated:` 等历史形式由查询兼容处理。历史 ID 之间的对应关系从尚存的系统日志和错误记录读取，缺失的对应关系不会通过字符串相似度补全。

<a id="request_query"></a>
系统模型请求也可通过各自的请求 ID 查询，管理员可用父测试 ID 关联同一轮的多个上游尝试。详情返回请求来源、系统用量完整性和已知提供商成本；系统记录没有用户或 Key 归属，普通用户无法读取。

## 查询与权限

- 管理员入口：`GET /api/v1/admin/requests?request_id=...`，或 `/api/v1/admin/requests/:request_id`。
- 用量、错误、系统日志、审计和审核列表支持 `request_id` 筛选。精确查询省略时间条件时读取仍在保留期内的数据。

`request_lookup_ids` 先按主键查本地请求 ID。未命中时，再查调用方、计费键、上游 ID 和历史日志。候选 ID、匹配的摘要和关联子请求分阶段保存为数组，后续查询用数组匹配索引列。外部计费键按每个候选值分别查索引，阻止缺少表达式索引统计时把关联规划成用量表全扫。计费记录继续按计费键和 API Key 匹配。

详情查询先解析一次候选 ID，摘要、用量、错误和审计查询共用这组数组参数，各来源继续检查用户和团队范围。用量列表、统计、Ops、审计和审核筛选通过 `ARRAY(SELECT ...)` 计算候选数组，再用 `= ANY(...)` 匹配各 ID 列。审计记录使用 `(request_id, created_at DESC)` 索引。

请求详情的用量查询在一条 SQL 内分别匹配请求 ID、兼容的上游 ID 和系统请求父 ID。候选只携带用量行主键、时间和归属字段，合并去重后先过滤权限，再统一排序截取最新 101 行，最后按主键读取详情。同一行命中多个来源只返回一次，相同请求 ID 下的不同用量行分别保留。分支内不单独按时间排序限量，避免新表达式索引缺少统计信息时改用时间索引遍历大量历史行。

查询回归覆盖稀疏命中、外部别名、同名冲突和计费表达式索引缺少统计的升级状态。PL/pgSQL 函数的外层执行计划显示函数调用，测试通过 `auto_explain.log_nested_statements` 检查内部查询，并分别覆盖按参数规划和复用通用计划的情况。性能判断检查实际访问的用量、请求摘要、错误、系统日志和审计表。

详情用量查询还覆盖系统元数据及父 ID 表达式索引缺少统计的状态，在默认扫描配置下检查完整 SQL 的实际扫描行数和过滤行数。仅排除顺序扫描不足以发现按时间索引遍历历史数据的问题。新增表达式索引后，刷新用量表统计有助于恢复准确估算；查询本身也需要通过缺少统计时的回归。

命中已保存的本地请求 ID 时，查询使用该请求、摘要中登记的计费及历史引用和父子关系。调用方和上游别名的展开适用于未命中本地 ID 的搜索。用量、错误和系统日志也遵循这个顺序，其他请求的外部字段与本地 ID 同名时，精确查询保持本地请求的范围。

父请求查询同时解析关联子记录的计费键和历史引用。任务在更新程序之前已经生成用量记录时，通过子记录的 API Key 与计费键找到这条记录。子任务的发起请求和之后的轮询请求都可以查询这份用量。

响应中的 `items` 包含请求摘要、用量及错误引用，父请求查询包含其任务和轮次。同一个外部 ID 可以匹配多次请求，超过 100 条时返回 `has_more`。

前端的 `/admin/requests` 是管理员请求查询页，按状态、阶段耗时、上游尝试、用量和错误展示每条匹配的请求。请求的失败阶段计时和每条用量的性能各画一条时间线，以请求总耗时为刻度。每次上游尝试列出它的上游请求 ID、读取该 ID 的响应头和响应 ID，关联标识区列出其余标识。`RequestIdLink` 为管理员提供详情链接，其他身份显示文本和复制按钮。使用记录、错误、系统日志、审计和审核列表都能按请求 ID 筛选。使用记录页的请求 ID 在漏斗筛选面板里，按回车或离开输入框后生效。筛选期间查询不带日期范围，使用记录页隐藏分布图和趋势图，汇总与导出使用相同的筛选条件。

请求详情与写入状态接口使用管理员认证，处理器在读取数据前再次检查管理员角色。普通用户可以按请求 ID 筛选自己的使用记录并复制 ID。用户端的 `/requests` 页面和 `/api/v1/requests` 接口已移除。请求 ID 本身不赋予访问权限。
