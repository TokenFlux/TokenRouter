# R01：刷新等待者在停止期间被放行

用户在 S12 提交 `f7f970c3d` 后明确要求修复该失败；本次只调整 R01 范围，不扩展历史问题排查。原失败记录及 S12 先前验证资料保留。

## 原因与最小修复

`operationActivity.stop` 先设置停止状态，再在锁外逐个取消已接纳的任务。持有账号锁的管理刷新可能先收到取消并释放锁；排队后台刷新尚未被取消，原先只检查 `ctx.Err()`，从而启动供应商交换。该问题依赖调度时序，与数据库、支付迁移或多实例无关。

统一刷新锁取得本地锁后，通过同一生命周期互斥锁复查停止状态。停止已生效则返回 `context.Canceled` 并释放本地锁，不再取得 Redis 锁、回读账号或执行交换。新请求仍返回原 `ErrRefreshStopped`。正常刷新、原取消来源、凭据条件写入和分布式锁降级规则保持。

## 复现与验证

- 原偶发测试独立重复 1,000 次通过，未把这一结果当成问题不存在。
- 新增 `TestRefreshLockRejectsStoppedOwnerBeforeCancellationArrives` 固定停止状态已发布但逐项取消尚未传播的间隙；测试闸门不依赖错误交错必然出现，不改变生产同步逻辑。
- 原实现普通三轮、使用 S12 原 HEAD 五个相关生产文件的 Go overlay 在 race 模式三轮均失败：等待者被错误放行，返回 nil 而非取消错误。原文件摘要与修复前当前文件一致。
- 修复后管理刷新、导入刷新、停止和锁回归 race 重复 100 轮通过；原管理/后台共享锁测试断言未更改。
- 普通全量 11,754 条通过、4 条既有跳过、无失败；unit 直接消费者 race 60 条、integration 标签刷新 race 17 条通过且无跳过。后者为进程内生命周期测试，不冒充真实数据库竞争验证。
- normal/unit/integration 增量 lint 无新增诊断；仅比较本次改动，S12 原全量 lint 基线 1 / 284 / 17 继续保留。命令、退出码与日志见 [结果](results.json)。

撤销修复会重新允许停止期间的排队刷新启动交换。不涉及 SQL、Ent、Wire、缓存协议或金额变化。
