## 2. 固定问题与修复决策

九个复现场景在 race 模式下连续三轮均触发相同失败断言。它们是原实现的问题证据，不计测试通过。

| 编号 | 已复现问题 | 本阶段修复 |
| --- | --- | --- |
| B01 | 支付后台重复 Start 会重复执行首轮；Stop 后 Start 仍领取任务 | 统一启停屏障，重复启动幂等，停止不可逆；保留首次立即执行 |
| B02 | Stop 不取消支持 context 的在途查询，随后仍可能继续其他阶段 | 运行 context 贯穿锁、查询、渠道请求和阶段切换；停止先取消，再按应用剩余预算等待 |
| B03 | 首次渠道加载失败后仍标记已加载；刷新失败清空旧注册表 | 加载成功才标记完成；先构造完整候选表再原子发布，整体读取失败保留旧表并允许后续重试 |
| B04 | 迟到的退款失败结果将已成功退款覆盖成 `REFUND_FAILED` | 成功与失败均按认领状态、版本及本次退款身份条件更新；竞争失败读取当前事实，不覆盖新结果 |
| B05 | `REFUND_PENDING` 审计失败后，后续确认漏扣权益；即时成功审计失败却返回成功 | 必要退款记录与对应本地状态、资金变化同事务提交，保存可恢复扣减事实；缺失资料不得默认为无需扣减 |
| B06 | 单被邀请人返利上限为 10，并发两次计提实际累计到 16 | 在同一事务内锁定邀请人推广档案，再读取累计、计算剩余额度并写入返利；返回实际计提金额 |

B03 保留原有单个配置无效时的处理方式和旧订单实例绑定规则，不扩大 registry fallback。

### B05：保留现有退款时序

用户已选择保留“先扣权益，渠道失败或待确认时回退”的行为，采用短事务衔接：

1. **本地准备事务**：锁定并认领订单，调用 billing 参与能力完成预扣，同时在现有支付审计表写入必要恢复记录。记录本次退款标识、金额、扣减意图、实际扣减、订阅信息和操作版本；失败则整体回滚，不能调用渠道。
2. **渠道调用**：事务外执行，沿用原订单、金额及渠道幂等键，不把新增内部标识加入旧渠道幂等编码。
3. **明确失败或待确认**：将原补偿操作、状态和必要恢复记录放入闭合事务。待确认记录保留原 JSON 字段，并关联准备记录。
4. **即时成功**：成功状态与成功审计原子提交，不再次扣减。若最终落库失败，保留先前已提交的准备事实及可恢复状态，返回错误，不能声称渠道退款已经撤销。
5. **待确认最终成功**：继续将认领、实际权益回收、订单完成和成功审计放在同一事务；失败整体回滚。
6. **恢复**：现有管理员退款查单入口支持带有效恢复记录的 `REFUNDING`，页面开放已有查单动作，不新增 URL。查明成功后幂等完成；不支持渠道查单、结果不明或历史资料缺失时明确提示人工核实，不盲目重发退款或猜测扣减。

恢复记录使用现有审计表，带明确格式版本并兼容原 `REFUND_PENDING` 记录；不新增数据库列。普通支付过程审计仍保持原尽力语义，只有退款正确性依赖的记录变为强制持久化。

## 3. 迁移步骤与接口

### S12.0：冻结输入与资金账本

记录 HEAD、索引、工作区、工具版本、源码摘要、SQL checksum、Ent/Wire 摘要和 S11 完整诊断，归档规划证据。

### S12.1：promotion 与事务参与

- promotion 拥有邀请码、关系绑定、专属比例、冻结/解冻、返利记录、转入余额、Promo 管理和注册应用；HTTP 与 PostgreSQL 分别进入 Adapter。
- 核心使用独立实体、用户展示投影、运行设置读取接口和明确时间输入，不接收旧 User、完整 config、Ent 或 SQL 事务。
- Promo 的锁码、事务内校验、加余额、usage 和次数保持同事务；返利转入的认领、清零、余额、累计充值和转账记录保持同事务。
- billing 提供命名明确的事务内余额能力，保留 Promo 赠送、返利转入、普通加款与累计充值的差异；参与方法不独立提交或发布缓存失效。
- 落实 B06：存储 Adapter 锁定最新状态，核心执行比例、期限、上限和八位舍入规则；支付外层事务通过参与工厂复用同一连接。
- 保留来源订单与支付返利审计的去重边界、邀请码规范化、一次绑定、冻结时间和现有查询排序。
- identity 注册、billing 兑换及管理员调账直接绑定新 promotion 窄接口，删除对应旧桥接。提交后缓存失效继续保持原顺序和失败语义。

### S12.2：payment 核心、配置与渠道

保留现有 `internal/payment` 和 `provider` 路径，将旧支付用例迁入唯一实现：

- 核心拥有订单、商品/渠道快照、费用与币种规则、实例选择、registry、下单、查单、文档链接、统计和续接令牌。
- 将 Ent 查询、实例配置读取和存储移入 PostgreSQL Adapter；具体渠道构造、配置/密钥/环境变量投影及 Wire 装配移到 app。
- 保留五类渠道及现有子支付方式、轮询/最小金额选择、限额耗尽回退、批量用量查询和原查询失败语义。
- 保留金额类型、计算顺序、币种最小单位与容差、手续费、充值倍率及套餐汇率；不重写金额算法。
- 保留订单与 provider instance 绑定、商户身份校验、商品快照、历史配置解密兼容、配置脱敏和删除限制。
- 落实 B03，生产只持有一份注册表、选择计数与配置运行实例。
- HMAC 续接令牌、旧密钥验证、24 小时/15 分钟 TTL、公开最小查单和返回地址规则保持。微信支付授权的 cookie/state/redirect 留 HTTP，OpenID 交换通过 app 注入现有能力，不复制身份认证实现。
- 套餐仍由 billing 唯一拥有，payment 仅保存购买快照并调用权益接口。

### S12.3：支付状态、履约与后台任务

- webhook、主动 verify、用户/管理员恢复和后台对账共用状态迁移及履约用例。
- 保留迟到成功、取消与付款竞争、处理中订单、五分钟履约 lease、原批次/游标和失败退避。
- 余额履约继续使用订单专属充值码，订阅使用 `source_order_id`；返利审计认领与返利写入保持同事务，不把原多阶段履约扩大成跨渠道长事务。
- 通知直接调用 notification；业务触发仍由 payment 决定，保持原去重、发送时点及邮件失败不撤销权益。
- 落实 B01/B02：构造不启动，立即首轮及原周期保持；运行 context 贯穿四类后台处理，停止后不开始下一阶段。
- 保留原 leader key、owner、TTL 和 Redis→数据库回退。app 绑定唯一后台实例与通知任务拥有者，沿用 HTTP 五秒、后台总计三十秒预算；超时报告未完成项，共享依赖不提前关闭。

### S12.4：退款及恢复

- 核心以独立 `RefundPlan`、扣减结果和恢复记录表达操作，不暴露 Ent 实体。
- payment PostgreSQL Adapter 拥有退款闭合事务，通过 app 注入 billing 的同连接余额/订阅参与能力；沿用原 Ent context，不新增事务 key。
- 落实 B04/B05，按第二节确定的时序处理准备、渠道结果、补偿、确认与恢复。
- 保留 `require_force`、管理员显式确认、实际可扣非负余额、原订阅调整/撤销规则、渠道退款比例和 pending/partial/refunded 形状。
- 旧恢复资料正常兼容；缺失、损坏或相互矛盾的记录返回明确待核实错误，不能以默认零值完成资金操作。
- 不新增自动渠道退款重试，不统一各渠道结果不明时的行为。

### S12.5：HTTP、装配、门禁与文档

- 用户/管理员支付、webhook、微信支付续接、推广与 Promo 路由直接绑定新 HTTP Adapter。
- 保留 URL、中间件顺序、权限、幂等 helper、JSON/Ent 历史展示形状、分页、统计、重定向和公开字段边界。
- webhook 保留原始 body/query、Header、验签顺序、订单实例验证及各渠道 ACK；通用解析不得提前消费签名输入。
- app 持有唯一服务、存储、registry、选择器和后台任务；旧入口只保留别名、投影或委托。
- 同批更新 depguard，删除 payment 的 Ent/config/Wire 历史许可及对应排除项；新核心禁止旧业务、Gin、config、具体存储/provider 和 app。
- 同步支付权益、推广返利、身份衔接、架构、配置、HTTP、运维及开发文档。明确退款各阶段保证，避免继续把即时成功和待确认分支描述成同一个原子事务。
