## 目录定位与成员

按以下顺序确定文档根：

1. 使用用户明确指定的路径。
2. 使用项目级技能门禁中声明的根 `index.md` 路径。
3. 复用仓库中唯一且用途明确的现有文档根。
4. 其他情况使用 `docs/`。

不要在文档根下再增加通用的 `project/` 中间层。存在多个可能的文档根且无法从项目指令判断时，在首次建库阶段询问用户。

通过根 `index.md` 或分类 `index.md` 规范列出的文档才属于 Project Doc。库外 README、法律材料、营销材料、生成文档和临时计划不因位于同一目录而自动纳入。

对文档库成员执行以下命名规则：

- Markdown 文件使用小写 `snake_case`，格式为 `[a-z][a-z0-9_]*.md`。
- 目录使用小写 `snake_case`，格式为 `[a-z][a-z0-9_]*`。
- 各级目录文件固定命名为 `index.md`。
- 建库备忘录固定命名为 `.project_doc_bootstrap.md`，它是唯一允许以点开头的文档库工作文件。
- 纳入文档库的遗留文件或目录不符合规则时，重命名并同步修复仓库内全部引用。
- 不为统一外观而重命名库外文档。

根据已有文档和项目指令判断主语言。保持已有语言边界，不自动生成双语副本；同一篇文档默认只使用一种主语言。

## 分级目录

根 `index.md` 是仓库任务的文档路由入口，首次读取后可以按读取规则复用。它应保持紧凑，仅包含：

- 文档库的用途和当前有效范围。
- 根级文档的一句话概要与读取时机。
- 每个现有分类的一句话概要、适用场景和分类 `index.md` 链接。
- 建库期间尚未完成的状态提示。

从以下稳定分类中按实际需要建目录，不创建空分类：

- `architecture/`：系统边界、组件关系、跨模块数据流和关键不变量。
- `domains/`：领域概念、业务规则、状态机和核心用语。
- `interfaces/`：公共 API、事件、数据格式、配置契约和集成边界。
- `operations/`：部署、迁移、故障恢复、观测、安全运行和维护流程。
- `decisions/`：需要保留理由、取舍和后果的架构决策记录。

分类 `index.md` 必须规范列出该分类内每篇文档。每篇文档只在一个分类目录中作为规范条目出现；其他位置使用普通“相关文档”链接，避免多个目录来源互相漂移。

目录条目统一表达三项信息：

```markdown
- [文档标题](relative_path.md)：一句话概要。读取时机：涉及哪些任务、代码区域或概念时读取。
```

建库期间可在条目前使用 `[planned]`、`[in_progress]`、`[verified]` 或 `[blocked]`。目标文件不存在时用代码格式显示计划路径，不创建失效链接。建库结束时移除所有临时状态。

## 文档内容与粒度

每篇当前状态文档应包含：

- 唯一 H1 标题。
- 开头的一段范围说明，明确本文覆盖和不覆盖的内容。
- 从当前代码、测试、配置或运行约束核实过的事实。
- 按语义组织的章节；只有被代码引用的章节才必须添加显式稳定 ID。
- 必要的相关文档链接，避免复制其他文档已经拥有的事实。

文档超过五个主要章节或需要多次局部读取时，在开头增加简短章节导航。导航只概述章节和读取条件，不重复正文。

新知识与现有文档具有相同主题、受众和演进周期时，扩展现有章节。满足以下条件时创建新文档：

1. 知识在当前任务结束后仍会长期有效。
2. 理解它需要跨越多个文件、模块、接口或运维边界。
3. 它具有可以独立描述的范围和读取时机。
4. 塞入现有文档会混合不同主题、受众或更新周期。

不要为单个函数即可表达的局部事实、机械重构、测试夹具、生成代码、临时实验、实施计划或工作进度创建当前状态文档。

## 读取规则

统一遵循 [SKILL.md 的读取与上下文复用规则](../SKILL.md#读取与上下文复用)。根据任务关键词、代码路径和已知索引中的“读取时机”选择分类 `index.md`，再选择具体文档；只补读尚未获取、已遗失或需要刷新的内容。

读取具体文档时遵循最小充分原则：

- 优先读取锚点目标章节。
- 补读理解该章节必需的范围说明、术语和直接依赖章节。
- 只有跨域任务或目录无法完成路由时才扩大阅读范围。
- 建库备忘录存在时，在根目录之后立即读取并以其“下一步”为恢复入口。

## 更新规则

以下变化必须重新评估并同步相关文档：

- 对外或跨模块行为、接口、事件、错误语义发生变化。
- 领域规则、状态转换、不变量、权限或安全边界发生变化。
- 配置、数据模型、迁移、部署、恢复或观测流程发生变化。
- 代码或文档移动导致路径、符号所有者、普通链接或锚点变化。
- 工作中发现文档与已核实的当前行为不一致。

纯内部重构且文档描述的语义不变时，不改写正文；只维护因移动而失效的引用与锚点。

## 删除、移动与合并

只有主题已经从当前系统消失、没有仍受支持的消费者且有效知识没有被其他文档需要时，才删除当前状态文档或章节。

删除前必须：

1. 搜索根目录、分类目录、其他文档和全部 `@project-doc` 锚点。
2. 判断有效内容应删除、迁移还是合并到其他文档。
3. 在同一变更中更新目录、普通链接、锚点和相关说明。
4. 再次搜索旧路径和旧章节 ID，确认没有残留引用。

仍受支持但已经弃用的功能必须保留状态、替代方案和迁移路径。临时关闭或功能开关默认关闭不构成删除理由。

移动文档不改变其语义身份；尽量保留章节 ID，并原子更新所有路径。合并文档时为仍被引用的语义选择明确目标章节，不把多个旧锚点随意指向整篇新文档。

## ADR

重要且未来可能被重新质疑的设计取舍写入 `decisions/`。ADR 至少记录状态、背景、决策、取舍、后果和相关文档。

已接受 ADR 的历史背景不随当前实现反复改写。新决策替代旧决策时：

- 新建 ADR 并说明替代关系。
- 将旧 ADR 状态改为 `superseded` 并链接新 ADR。
- 将当前代码锚点和当前状态文档指向仍然有效的决策或说明。

## 证据与冲突

代码、测试和文档冲突时，把它标记为漂移候选，不默认任何一方获胜。结合以下证据核实意图：

- 用户当前任务和明确的公共契约。
- 可执行测试、schema、配置验证和接口定义。
- 调用方、数据流和实际错误处理。
- 当前状态文档、ADR 和可用的变更历史。

如果证据能确定意图，在用户授权范围内修复错误的一侧并同步其余引用。高影响歧义无法消除时停止相关修改并询问用户。

## 结构检查

完成写任务前，根据变更差异检查受影响文档、所属目录条目和相关入站、出站引用；已有检查结论在相关内容未再变化时可以复用。下列检查项按影响范围适用，不要求每次重读根索引、所有分类目录或扫描全库。首次建库验收或明确要求全库一致性审计时，才覆盖整个文档库：

- 根目录和分类目录中的链接目标存在。
- 每篇 Project Doc 文档拥有一个规范目录条目。
- 文件、目录和显式章节 ID 符合小写 `snake_case`。
- 同一文档内没有重复章节 ID。
- 所有 `@project-doc` 路径和章节 ID 都存在。
- 移动或删除后的旧路径、旧 ID 和失效链接没有残留。
- 建库完成后不存在临时状态和建库备忘录。
- Git diff 中没有空白错误，代码变更对应的测试已经执行。

使用仓库已有工具以及 `rg`、必要的局部读取和 Git diff 完成检查；移动或删除时可全仓搜索旧路径和旧 ID，以找全引用。不为此默认生成项目脚本或 CI。
